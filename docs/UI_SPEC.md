# UI_SPEC — что фронт показывает и откуда берёт данные

Статус: **черновик для сверки с фронт-командой.** Состав экранов, раскладка и
визуальные решения — зона фронта; здесь то, что фронт не может решить сам: какие
витрины существуют, какие поля **нельзя** считать заново и о чём экран обязан
предупредить словами. Спорные места помечены «❓» — это вопросы к вам.

Относящиеся документы: `docs/SCHEMA.md` (§1 справочный слой, §2 контракт прогона,
§2а приёмка), `docs/PLANNER_SPEC.md` (§6 KPI, §7 приёмка), `docs/DECISIONS.md`
(ADR-001, 007, 016, 017, 019), `docs/RUNBOOK.md` (§8 приёмка сервера).

## 0. Как получить данные

Один маршрут на все витрины:

```
GET /api/views/{view}?run_id=&limit=&offset=&order=
GET /api/views                      # справочник: имена, колонки сортировки, экран
```

| Параметр | По умолчанию | Что делает |
|---|---|---|
| `run_id` | последний прогон со `status = 'ok'` | какие данные прогона показать; у справочных витрин параметра нет — передадите, получите 400 |
| `limit` | 500 | размер страницы; потолок 5000, выше — 400 |
| `offset` | 0 | смещение; `count` тогда считается отдельным `COUNT(*)` |
| `order` | порядок витрины | `team_id,-gap_hh` («-» = DESC); колонки — только из белого списка витрины, иначе 400 |

Ответ — **строка витрины как есть** плюс конверт:

```json
{
  "view": "v_role_deficit", "kind": "view", "screen": "Роли и ёмкость",
  "note": "Главная аналитическая витрина: дефицит по «команда × роль»…",
  "run_id": null, "run_column": null, "run_default": false,
  "as_of": "2026-09-21T19:41:38+03:00",
  "order": ["team_id", "role_name"],
  "limit": 500, "offset": 0,
  "count": 76, "returned": 76, "truncated": false, "has_more": false,
  "columns": ["team_id", "role_name", "demand_hh", "supply_hh", "gap_hh", "verdict"],
  "items": [{"team_id": "Team-Alpha", "role_name": "Руководитель проекта",
             "demand_hh": "140.00", "supply_hh": "0", "gap_hh": "140.00",
             "verdict": "роли нет в команде"}]
}
```

Правила чтения конверта, которые лучше не нарушать:

* **`as_of` показывать в шапке каждого экрана.** Данные берутся из базы на момент
  запроса; между экранами он разный, и без этой подписи цифры «плывут» незаметно.
* **`run_id` показывать там, где он не `null`.** В шапке — номер прогона, иначе
  заказчик не поймёт, почему план от 3-го спринта отличается от Недели 0.
  Данные для выпадашки — `GET /api/views/plan_runs` (2 прогона, порядок `-run_id`).
* **`count` ≠ `returned`** при обрезании: показывайте «45 из 300», иначе список
  молча врёт. `has_more` — для подгрузки следующей страницы по `offset`.
* **`columns`** приходит и при пустом `items`: пустая таблица всё равно рисуется
  с шапкой, а не «белым экраном».

Коды ответов — разные, и их полезно различать в UI:

| Код | `error` | Что показать |
|---|---|---|
| 200 | — | данные (в том числе пустая витрина: `count: 0`) |
| 400 | `bad_request` | ошибка фронта: неизвестный `order`, `limit` > 5000, `run_id` у справочной витрины. В теле — `param` и `known` (список допустимых значений) |
| 404 | `not_found` | опечатка в имени витрины; в теле — `known` со всеми 25 именами |
| 503 | `database_unavailable` | база не отвечает: `message`, `dsn` без пароля, `hint`. Это не баг фронта — блок «API недоступен» + «запустите `run.bat`» |

Кэша нет: сервер отдаёт `Cache-Control: no-store`. Каждый экран делает свой
запрос — это и даёт честный `as_of`.

### 0.1. Про типы в JSON — важнее, чем кажется

`numeric` PostgreSQL приходит **строкой**, а не числом: `"140.00"`. Это следствие
точности (часы и SP не переводим в float на сервере) и `json.dumps(default=str)`.
Значит на фронте:

```ts
const demand = Number(row.demand_hh)   // "140.00" → 140
row.gap_hh.startsWith('-')             // знак дефицита — так, а не через '< 0'
```

| Тип в базе | В JSON | Пример |
|---|---|---|
| `numeric` (часы, SP, KPI) | строка | `"demand_hh": "199.00"`, `"value": "6.67"` |
| `integer` / `smallint` | число | `"priority_rung": 67`, `"orbit_count": 1` |
| `boolean` | `true` / `false` | `"estimate_disputed": true` |
| `date` | строка `ГГГГ-ММ-ДД` | `"planned_end": "2026-07-10"` |
| `timestamp with time zone` | ISO-8601 со смещением | `"created_at": "2026-09-21T16:19:08.323258+03:00"` |
| `ARRAY` / `jsonb` | массив / объект | `"skills": ["Java", "Spring Boot"]`, `"payload": {...}` |

`null` встречается часто и это нормально: у переносов нет `start_sprint`, у задач
`ToDo` нет `actual_start`. Рисовать это как «—», а не как 0.

## 2. Экраны

### 2.1. Доска задач

**Витрина `v_task_board`** (45 строк, 24 колонки, порядок по умолчанию
`priority_rung,task_id`) — денормализована, джойнить не надо.

Поля экрана: `task_id`, `prodf_id` + `br_id` (инициатива), `summary`, `status`
(`ToDo` 31 / `InProgress` 6 / `Done` 8), `team_id`, `priority_rung` и `rung`
(скоринг инициативы, ADR-005), `estimation_sp`, `estimated_hh_effective` (истина —
сумма столбца матрицы сметы, ADR-002), `estimated_hh_declared` (что обещали в
исходнике), `estimate_disputed` (**true у 24 из 45 задач!**), `remaining_hh`
(сумма по доске 6746 ЧЧ), `planned_start` / `planned_end` / `actual_start` /
`actual_end`, `topo_order`, `depth`, `earliest_start_sprint`, `on_critical_path`
(19 задач), `blocked_by` / `blocks` (число связей: графа зависимостей по задачам
эта витрина не отдаёт).

| Пустое состояние | Что писать |
|---|---|
| витрина пуста | «Задачи не загружены: проверьте `run.bat` и `v_dq_summary`» |
| фильтр ничего не нашёл | «По фильтру задач нет» + кнопка «сбросить», а не пустая таблица |

**Текст, который экран обязан показать** (иначе с цифрами спорят):

* `estimate_disputed = true` — «оценка спорная: столбец матрицы и заявленная смета
  расходятся (25 находок `ESTIMATE_SOURCES_DISAGREE`). Показываем
  `estimated_hh_effective` — 100 ЧЧ, в исходнике 130».
* `planned_start` / `planned_end` — **это история из исходного файла, а не наше
  обязательство** (ADR-016). Именно из-за него появляются предупреждения
  `PLANNED_END_OVERSAIL`.
* `remaining_hh` — остаток на момент выгрузки, а не «сколько ещё будут делать».

**Витрина `tasks`** — карточка задачи: `result_planned`, `result_customer`,
`result_executor`, `result_final` (с ними связаны «варианты выбора цели» из
`ref_result_options`), `spent_time_declared`, `committed_week0`.
⚠ `committed_week0` заполнен только у 8 задач `Done` — знаменатель KPI берётся из
`plan_baseline`, а не из этого поля (ADR-004).

**Витрина `v_task_remaining_hh`** (258 строк) — часы **по ролям**:
`estimated_hours`, `spent_hours`, `remaining_hours`. Это оценка по ролям, суммы по
задаче в витрине нет и складывать их нельзя (ADR-002) — получится больше реальности.
### 2.2. План квартала (гант)

**Витрина `plan_task_schedule`** (37 строк, порядок по умолчанию
`task_id,start_sprint`, фильтруется по прогону):

| Поле | Смысл |
|---|---|
| `start_sprint`, `end_sprint` | спринты 1–7; **пусты у переносов** — не ошибка, смотрите `decision` |
| `forecast_end_date` | дата окончания по прогнозу планировщика |
| `decision` | `in_quarter` (7 задач) / `deferred_next_pi` (30) / `cancelled` |
| `decision_reason` | код причины переноса — объяснение для заказчика, показывать рядом с задачей |

Сетка квартала — **`sprints`** (7 строк): `sprint_no`, `start_date`, `end_date`,
`length_days`. **7-й спринт короткий: 23–30.09, 8 дней**, а не 14. Отсюда
множитель фонда `v_sprint_fund_factor.factor = 0.5714` (спринты 1–6 — `1.0000`) и
общий `v_pi_fund_factor.factor = 6.5714` при 92 днях.

**Витрина `v_plan_assignment_detail`** (18 строк на прогон) — «кем закрыто»:
`engineer_id`, `hours`, `home_team_id` + `serving_team_id` (разошлись = заём),
`is_loan` (считает СУБД — **не пересчитывать**), `served_role` / `native_role`,
`is_substitution` (сейчас всегда `false`: замещения отклонены организаторами,
ADR-010), `grade`.

**Витрина `plan_baseline`** — базовая линия Недели 0: `task_id`, `planned_sp`,
`committed`. ⚠ **Она есть только у канонического базового прогона** — сейчас это
`run_id = 1` (`as_of_sprint = 0`, 37 строк). У прогона по умолчанию (`run_id = 2`,
пересчёт на 3-м спринте) она пуста, и это нормально: экран базовой линии должен
спрашивать её с `run_id=1`, а не с «текущим». Канон по ADR-004:
`MIN(run_id) WHERE as_of_sprint = 0 AND status = 'ok'`.

Проверено на живой базе 21.09.2026: `GET /api/views/plan_baseline` (прогон по
умолчанию) → `count: 0`, `GET /api/views/plan_baseline?run_id=1` → 37 строк.
Поэтому базовую линию и «текущий план» нельзя рисовать из одного запроса: это два
запроса с разными `run_id`, и в шапке гант-экрана это стоит подписать.

**Пустое состояние:** «В квартал взято 7 задач из 37, остальные перенесены на
следующий PI — это решение планировщика, а не сокращение бэклога».

### 2.3. Алерты

**Витрина `alerts`** (23 строки в прогоне 2, порядок `sprint_no,level,alert_id`):
`level`, `alert_type`, `entity_type` + `entity_id`, `message`, `payload`.
`message` — готовый текст по-русски, можно показывать как есть:

> `{"alert_id": 21, "sprint_no": 1, "level": "orange", "alert_type": "role_deficit",
> "entity_type": "role", "entity_id": "Аналитик 1С", "message": "роль «Аналитик 1С»:
> 10.00 ЧЧ на 1 задачах, фонд 0 ЧЧ — нужен наём или дообучение",
> "payload": {"verdict": "НАЙМ: закрыть некем", "role_id": 2, "supply_hh": "0"}}`

Сейчас в прогоне 2: **red / `deadline_miss` — 14**, **orange / `role_deficit` — 6**,
**yellow / `cascade_shift` — 3**. `payload` — для перехода на другие экраны.

**Витрина `v_plan_violations`** (7 строк) — предупреждения контракта: все 7 —
`PLANNED_END_OVERSAIL`, `severity = 'warning'`, `error` = 0. Текст для плашки:

> «Прогноз выходит за даты исходного плана. Это не срыв: даты в исходнике —
> история, план по ним не строился (ADR-016). Ошибок контракта нет: `error` = 0».

**Пустое состояние:** `count: 0` — «предупреждений нет», зелёная плашка, а не
«ошибка загрузки».

### 2.4. KPI

**Витрина `kpi_snapshots`** (9 строк на прогон: 1 `pi_predictability`,
`sprint_count` строк `say_do_ratio`, 1 `bus_factor`):

| Код | Сейчас (прогон 2) | `target_min` | `target_max` | Что говорить словами |
|---|---|---|---|---|
| `pi_predictability` | **6.67** | 80.00 | 100.00 | красная плашка: «в квартал попало 7 задач из 45, поэтому показатель низкий — это свойство плана, а не сбой пересчёта» |
| `say_do_ratio` | 0.00 в спринтах 1–2, 100.00 в 3–7 | 90.00 | 105.00 | текст берём из `details.note`: «сравниваем план с обещанием Недели 0; задача, уехавшая из своего спринта, роняет показатель этого спринта» |
| `bus_factor` | **0.00** | 1.00 | — | «минимум по ролям со спросом: 7 ролей вообще без людей в штате — РП 449 ЧЧ, Разработчик 1С 107, поддержка 84 + 12, Аналитик 1С 10, Архитектор 1С 3» |

**Пороги красить только по `target_min` / `target_max` из строки**, во фронте их не
зашивать (SCHEMA §2): при пересчёте нормы могут измениться. Если `target_max` =
`null` (как у `bus_factor`), верхней границы нет — не рисовать `NaN`.

**`details`** — разбивка для тултипа: у `bus_factor` список `critical` ролей, у
`say_do_ratio` — `promised_sp` и `delivered_sp` (сейчас `"25"` против `"0"`).

**Витрина `plan_runs`** (2 строки) — выпадашка прогонов: `run_id`, `as_of_sprint`
(0 и 3), `status`, `created_at`, `params` (границы календаря внутри прогона).
❓ Вопрос 2: нужен ли выбор прогона в UI? Данные для него есть; если не нужен,
экран показывает «текущий» и подписывает `run_id` в шапке.

### 2.5. Роли и ёмкость

Здесь четыре разные вещи, и путать их нельзя.

**1. Дефицит по «команда × роль» — `v_role_deficit`** (76 строк): `demand_hh`,
`supply_hh`, `gap_hh`, `verdict`. Вердиктов два: «покрыто» (29) и «роли нет в
команде» (47). `gap_hh` **отрицательный, когда потребность покрыта**
(`-326.71`), поэтому знак читать строкой, а не `'< 0'` после `parseFloat`.
Вторая версия — **`v_role_deficit_effective`** (76 строк,
`supply_with_substitution_hh`): с учётом замещения. Сейчас цифры совпадают
(замещения отклонены, ADR-010), но витрины стоит показывать рядом: появится
разрешение на замещения — разойдутся, и это будет видно.

**2. Где нужен наём — `v_role_coverage_org`** (21 строка, порядок `-gap_hh`):
`native_people`, `people_incl_substitution`, `supply_hh`, `gap_hh`, `verdict`.
Сумма по вердиктам «НАЙМ: закрыть некем» = **665 ЧЧ на 6 ролей**:

| Роль | Спрос | Людей | Вердикт |
|---|---|---|---|
| Руководитель проекта | 449.00 | 0 | НАЙМ: закрыть некем |
| Разработчик 1С | 107.00 | 0 | НАЙМ: закрыть некем |
| Специалист поддержки | 84.00 | 0 | НАЙМ: закрыть некем |
| Специалист поддержки 1С | 12.00 | 0 | НАЙМ: закрыть некем |
| Аналитик 1С | 10.00 | 0 | НАЙМ: закрыть некем |
| Архитектор 1С | 3.00 | 0 | НАЙМ: закрыть некем |

**3. Незаменимость — `v_bus_factor`** (21 строка): `bus_factor`, `demand_hh`,
`risk`. Семь ролей «НЕТ В ШТАТЕ» (`bus_factor = 0`) и восемь «КРИТИЧНО (BF=1)» —
среди последних самые дорогие по спросу: ДевОпс (393 ЧЧ), Архитектор решений (329),
Разработчик Android (160), Дизайнер (155), iOS (140), Big Data (120), .net (90),
Руководитель BigData (42). Это готовый текст для слайда «риск исполнения».

**4. Ёмкость команды — `v_team_capacity_sp`** (6 команд) + `teams` (названия и
`focus_factor` = 0.80): `history_points` (2), `avg_velocity` (9.0–16.0),
`available_sp_per_sprint` (7.2–12.8), `available_sp_per_pi` (47.31–84.11).
Ещё есть **`v_engineer_role_coverage`** (30 строк) — какие роли закрывает инженер;
нужна, если экран показывает «кто может взять эту роль».

**Пустое состояние:** «В команде нет строк по этой роли» — это и есть вердикт
«роли нет в команде», а не ошибка.

### 2.6. Звёздная карта

**`v_orbit_map`** (30 инженеров) — готовая витрина: `engineer_id`, `role_name`,
`role_group`, `grade`, `total_capacity_rate` (`"1.00"` или `"0.50"` у парттаймеров),
`orbit_count` (26 инженеров на одной орбите, **4 — на двух**), `teams` (массив
team_id), `skills` (массив технологий), `bus_factor`, `risk` (8 «КРИТИЧНО (BF=1)»,
22 «ок»).

```json
{"engineer_id": "ENG-401", "role_name": "Разработчик Java", "grade": "Middle",
 "total_capacity_rate": "1.00", "orbit_count": 1, "teams": ["Team-L"],
 "skills": ["Apache Kafka", "Hibernate", "Java", "PostgreSQL", "Spring Boot"],
 "bus_factor": 7, "risk": "ок"}
```

грейд, ставка, команды, риск, `bus_factor` роли.

**`v_satellite_capacity`** (238 строк) — ёмкость по спринтам: `sprint_no`,
`length_days`, `capacity_rate`, `hours_own`, `is_shared_orbit` (час делится между
командами, ADR-001). Годится для тултипа «сколько часов в спринте 7» —
**`hours_own` уже умножен на множитель спринта**, пересчитывать вручную нельзя.
Пустая строка по спринту = «в этом спринте ёмкости нет», а не 0 часов.

## 3. Чего фронт **не** делает сам

Это список запретов, а не пожеланий: каждое из них уже было причиной расхождения
цифр между экранами.

| Нельзя | Почему | Делать так |
|---|---|---|
| Считать фонд квартала как «число спринтов × фонд спринта» (7 × 80 = 560) | квартал календарный, 7-й спринт 8 дней; правильный фонд 525.71 ЧЧ на ставку | брать `v_pi_fund_factor.factor` (6.5714) и `v_sprint_fund_factor.factor` |
| Повторять арифметику «92 дня / 14 дней» | единственный источник правды — `v_pi_fund_factor` / `v_sprint_fund_factor`; ручной расчёт разъедется с инвариантами и приёмкой | читать две вьюхи, множитель не считать |
| Зашивать нормы KPI (80–100, 90–105, > 1) в код фронта | нормы живут рядом со значением и могут измениться при пересчёте | красить по `target_min` / `target_max` из `kpi_snapshots` |
| Пересчитывать `is_loan`, `is_substitution`, `is_native` | это считает СУБД по `home_team_id <> serving_team_id` и правилам ролей | брать флаги из `v_plan_assignment_detail` / `v_engineer_role_coverage` |
| Считать «сколько часов в задаче», суммируя `v_task_remaining_hh` по ролям | в витрине строки «задача × роль», сумма завышает оценку (ADR-002) | показывать по ролям или брать `v_task_board.remaining_hh` |
| Выводить знаменатель KPI из `tasks.committed_week0` | заполнен только у 8 задач `Done` (ADR-004) | `plan_baseline` канонического прогона |
| Брать `plan_baseline` из прогона по умолчанию | у пересчёта на 3-м спринте базовая линия пуста по определению | `GET /api/views/plan_baseline?run_id=1` |
| Вычислять «текущий прогон» самому | правило одно для всех: `MAX(run_id) WHERE status = 'ok'` | не передавать `run_id` — сервер подставит `run_default: true` |
| Менять/писать что-либо через `/api/*` | сервер read-only: писать в контракт планировщика нечем и не нужно | планировщик запускается `uv run python tools/run_planner.py` |
| Кэшировать ответы дольше, чем живёт вкладка | `as_of` в шапке должен соответствовать данным | `Cache-Control: no-store` уже стоит; не «оптимизировать» кэшем браузера |

## 4. Три содержательные ловушки, которые нужно объяснить словами

Данные честные, но выглядят «как ошибка». Если не подписать — решат, что сломалось.

**1. `PLANNED_END_OVERSAIL` (7 warning).** Прогноз окончания выходит за
`planned_end` из исходного файла. Это ожидаемо: даты в исходнике — история
(ADR-016), план по ним не строился. `error` = 0 — контракт цел. Формулировка:
«прогноз позже исходного срока; срок в исходнике — факт истории, а не обещание».

**2. Алерты по ролям (6 orange).** «Роль «Аналитик 1С»: 10.00 ЧЧ на 1 задачах, фонд
0 ЧЧ — нужен наём или дообучение». Это следствие решения организаторов запретить
замещения ролей (ADR-010), а не дефект плана. Суммарно компания просит **665 ЧЧ
найма на 6 ролей**, из них 449 — руководитель проекта. Формулировка на экране:
«влияет на план только через наём или дообучение; замещения ролей запрещены
организаторами».

**3. «Красные» KPI (`pi_predictability` 6.67 при норме 80–100, `bus_factor` 0.00
при норме > 1).** Оба — свойство данных, а не сбой:
* предсказуемость считается от бэклога целиком, а в квартал попало 7 задач из 45;
* bus factor — минимум по ролям со спросом, а 7 ролей в штате отсутствуют вовсе
  (1С, поддержка, РП).
Формулировка: «показатель по определению жёсткий; смотреть вместе с числом задач
в квартале и списком ролей без людей».

## 5. Скорость и кэш

Замер на живой базе 21.09.2026 (`limit = 500`, 25 витрин подряд по HTTP — 2.26 с
целиком, сервер уже прогретый). Это **один прогон**: соседние запросы гуляют в
полтора-два раза, порядок величин важнее конкретных цифр.

| Витрина | Строк | Время | Размер ответа |
|---|---|---|---|
| `v_task_board` | 45 | 82 мс | 29 КБ |
| `tasks` | 45 | 61 мс | 28 КБ |
| `v_task_remaining_hh` | 258 | 57 мс | 30 КБ |
| `v_orbit_map` | 30 | 50 мс | 11 КБ |
| `v_satellite_capacity` | 238 | 54 мс | 63 КБ |
| `v_role_deficit` | 76 | 54 мс | 13 КБ |
| `v_role_deficit_effective` | 76 | 127 мс | 16 КБ |
| `v_role_coverage_org` | 21 | 218 мс | 5 КБ |
| `v_bus_factor` | 21 | 71 мс | 4 КБ |
| `plan_task_schedule` | 37 | 66 мс | 6 КБ |
| `v_plan_assignment_detail` | 18 | 90 мс | 6 КБ |
| `alerts` | 23 | 70 мс | 11 КБ |
| `kpi_snapshots` | 9 | 66 мс | 6 КБ |
| `v_plan_violations` | 7 | 101 мс | 2 КБ |
| `plan_runs` | 2 | 48 мс | 5 КБ |

Выводы, которые влияют на фронт:

* ни одна витрина не требует пагинации ради скорости: даже 258 строк — 57 мс.
  Пагинация нужна только «по смыслу» (доска, длинный список задач);
* **размер не связан со временем**: самые медленные — `plan_baseline` (279 мс
  при нуле строк в текущем прогоне), `v_role_coverage_org` (218 мс), `sprints`
  (180 мс), `v_engineer_role_coverage` (177 мс) и `ref_result_options` (168 мс);
  в них считаются вложенные вьюхи, а не отдаётся таблица. Если экран делает
  3–5 запросов сразу, показывайте скелетон, а не белый экран;
* справочник `/api/views` — 11 КБ и 31 мс, его можно звать один раз при старте
  приложения (но не кэшировать дольше сессии: состав витрин — часть контракта);
* первый запрос после старта сервера может занять секунды (соединение с базой,
  холодный кэш планировщика). Таймаут на своей стороне не делайте меньше 30 с —
  иначе экран покажет «ошибка» там, где просто медленно.

❓ Вопрос 4: если экран делает больше 3 запросов, скажите — соберём парный
эндпоинт под экран (пока нет ни одного такого запроса, и это сознательно: лишний
маршрут = лишняя сущность в контракте).

## 7. Как проверить локально (5 минут)

```bash
run.bat                                  # база + сервер + собранный фронт
curl http://127.0.0.1:8000/api/views      # справочник витрин
curl "http://127.0.0.1:8000/api/views/v_task_board?limit=2"
curl "http://127.0.0.1:8000/api/views/v_role_deficit?order=-gap_hh"
curl http://127.0.0.1:8000/api/views/nope             # 404 + known
curl "http://127.0.0.1:8000/api/views/v_task_board?order=1;--"   # 400 + known
```

`GET /api/views` — это ваш главный справочник: там имена витрин, экран, порядок по
умолчанию и полный список колонок, по которым можно сортировать. Расхождение с
этим документом считаем багом документа, а не сервера.
