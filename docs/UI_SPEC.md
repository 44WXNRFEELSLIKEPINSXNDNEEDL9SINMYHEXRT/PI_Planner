# UI_SPEC — что показывает интерфейс и откуда берёт данные

Этот документ — контракт между фронтом и сервером: какие витрины и маршруты
существуют, какие поля **нельзя** считать заново и о чём экран обязан сказать
словами. Оформление — в [UI_DESIGN.md](UI_DESIGN.md); схема данных — в
[SCHEMA.md](SCHEMA.md); правила планировщика — в [PLANNER_SPEC.md](PLANNER_SPEC.md)
и [ALGORITHMS.md](ALGORITHMS.md).

Календарь: PI начинается с начала календарного квартала и состоит из шести
двухнедельных спринтов (ADR-025). Границы, число спринтов и множители фонда —
**только из данных** (`sprints`, `v_sprint_fund_factor`,
`v_pi_fund_factor`), не из констант фронта.

## 0. Как читать данные

Один маршрут на все витрины:

```
GET /api/views/{view}?run_id=&limit=&offset=&order=
GET /api/views                      # справочник: имена, колонки сортировки, экран
```

| Параметр | По умолчанию | Что делает |
|---|---|---|
| `run_id` | последний прогон со `status` `ok` или `infeasible` | какой прогон показать; у справочных витрин параметра нет — получите 400 |
| `limit` | 500 | размер страницы; потолок 5000, выше — 400 |
| `offset` | 0 | смещение; `count` считается отдельным `COUNT(*)` |
| `order` | порядок витрины | `team_id,-gap_hh` («-» = DESC); колонки только из белого списка витрины, иначе 400 |

Ответ — **строка витрины как есть** плюс конверт:

```json
{
  "view": "v_role_deficit", "kind": "view", "screen": "Роли и ёмкость",
  "note": "…", "run_id": null, "run_column": null, "run_default": false,
  "as_of": "2026-09-21T19:41:38+03:00",
  "order": ["team_id", "role_name"], "limit": 500, "offset": 0,
  "count": 76, "returned": 76, "truncated": false, "has_more": false,
  "columns": ["team_id", "role_name", "demand_hh", "supply_hh", "gap_hh", "verdict"],
  "items": [{"team_id": "Team-Alpha", "role_name": "Руководитель проекта",
             "demand_hh": "140.00", "supply_hh": "0", "gap_hh": "140.00",
             "verdict": "роли нет в команде"}]
}
```

Правила чтения конверта:

* **`as_of` показывать на каждом экране.** Данные берутся на момент запроса, и без
  отметки цифры на разных экранах «плывут» незаметно. В интерфейсе это отметка
  «Ответ API»; рядом отдельная отметка «Расчёт плана» с временем прогона.
* **`run_id` показывать там, где он не `null`.** Иначе непонятно, почему план
  после пересчёта отличается от базового. Список прогонов — `plan_runs`.
* **`count` ≠ `returned`** при обрезании: показывать «45 из 300», иначе список
  молча врёт. `has_more` — для подгрузки по `offset`. Хук `useView` забирает все
  страницы сам и падает, если число строк изменилось во время загрузки.
* **`columns`** приходит и при пустом `items`: пустая таблица рисуется с шапкой.

Коды ответов:

| Код | `error` | Что показать |
|---|---|---|
| 200 | — | данные (в том числе пустая витрина: `count: 0`) |
| 400 | `bad_request` | ошибка фронта: неизвестный `order`, `limit` > 5000, `run_id` у справочной витрины; в теле `param` и `known` |
| 401 | — | экран входа (§3) |
| 404 | `not_found` | неизвестная витрина; в теле `known` со всеми именами |
| 429 | — | слишком много неверных токенов: подождать минуту |
| 503 | `database_unavailable` | база не отвечает: `message`, `dsn` без пароля, `hint`; в шапке красный значок API |

Кэша нет: сервер отдаёт `Cache-Control: no-store`.

### 0.1. Типы в JSON

`numeric` PostgreSQL приходит **строкой**: `"140.00"`. Часы и SP не переводятся
в float на сервере. На фронте:

```ts
const demand = Number(row.demand_hh)   // "140.00" → 140
row.gap_hh.startsWith('-')             // знак — строкой, а не через '< 0'
```

| Тип в базе | В JSON | Пример |
|---|---|---|
| `numeric` (часы, SP, KPI) | строка | `"demand_hh": "199.00"` |
| `integer` / `smallint` | число | `"priority_rung": 67` |
| `boolean` | `true` / `false` | `"estimate_disputed": true` |
| `date` | `ГГГГ-ММ-ДД` | `"planned_end": "2026-07-10"` |
| `timestamptz` | ISO-8601 со смещением | `"created_at": "2026-09-21T16:19:08+03:00"` |
| `ARRAY` / `jsonb` | массив / объект | `"skills": ["Java"]`, `"payload": {…}` |

`null` встречается часто и это нормально: у переносов нет `start_sprint`. Рисовать
как «—», а не как 0.

## 2. Что показывает каждый экран

### 2.1. Сводка

Главное по кварталу на одном экране; каждая плитка ведёт в свой раздел.

* **Задач в квартале** — число задач с решением `in_quarter` и приписка «из N».
  Не красится: норма не задана.
* **Три KPI** — последнее значение: факт, если он есть, иначе прогноз; плитка
  подписана «Факт» или «Прогноз». Окраска по границам нормы из строки KPI.
* **Рисков в прогоне** и **Вопросов к данным** — счётчики с подсказкой («Критичных:
  N», «Блокируют план: N»). Правила окраски — в [UI_DESIGN.md](UI_DESIGN.md) §3.2.
* Ниже: причины переноса задач с действием на каждую («что делать» — справочник в
  коде `PlanSummary.tsx`), таблица рисков по типам и таблица ролей с самым
  большим дефицитом часов.

### 2.2. ИИ-ассистент

Контракт — [openapi/assistant.yaml](openapi/assistant.yaml), правила ответов —
[ASSISTANT_RULES.md](ASSISTANT_RULES.md). Экран собран только из этих маршрутов; логики
ответов во фронте нет.

* **Чаты.** `GET /api/assistant/conversations` (новые сверху, курсор). «Новый чат» сразу
  открывает пустой чат без диалога; сам чат создаётся первым вопросом с темой и моделью,
  выбранными под полем ввода: `knowledge` (прогон не нужен) или `planning` (`pi_id`,
  `scenario_id`, `run_id` выбранного в шапке прогона). Режим приватности выводится из модели:
  внутренняя — `local_only`, внешняя — `configured`. Последняя модель запоминается в браузере.
  Заголовок задаёт сервер; переименование — `PUT …/title`, удаление — `DELETE …/{id}` (меню ⋮
  в истории и кнопки в шапке чата; чат с активным заданием не удаляется).
* **Под полем ввода.** Смена модели у начатого чата — `PUT …/settings`; переход с локальной
  модели на внешнюю требует подтверждения. Чат «о системе» можно подключить к прогону
  (`POST …/context`); обратно в «о системе» он не переключается. Если модель чата удалена,
  поле выбора подсвечено и просит выбрать другую.
* **Детали чата** (контекст, модель, рекомендации) открываются кнопкой в шапке чата: на широком
  экране колонкой справа, на узком — выдвижной панелью. Вопрос без ответа в истории помечен
  «Ответ не получен», у последнего — «Повторить».
* **Сообщения.** История — страницами по 50 (`next_cursor`), клиент загружает все. Отправка:
  `POST …/messages` с `text`, `expected_context_revision`, `expected_last_message_id` (ровно эти
  три поля) и обязательным `Idempotency-Key`; ответ `202` с `job_id`. Дальше опрос
  `GET /jobs/{id}` раз в ~1 с до `completed`, `failed`, `cancelled` или `expired`; остановка —
  `POST /jobs/{id}/cancel`. Ошибка обработки приходит в `job.error`, а не HTTP-статусом;
  `409` означает расхождение версии контекста или последнего сообщения.
* **Ответ.** `status` (`answered`, `needs_clarification`, `insufficient_data`), `summary`,
  `explanation`, `recommendations[]`, `clarification`, `limitations[]`, `entity_refs[]`,
  `evidence_ids[]`, `sources[]`. Уточнение — обычный ответ, не ошибка; повторяющийся текст
  уточнения и вывода показывается один раз. Ответ занимает всю ширину ленты; `explanation`
  отображается как Markdown (GFM: списки, таблицы; HTML не выводится), «Ограничения» свёрнуты. URL интерфейса из ответа не приходит: ссылка на
  сущность собирается из типа и идентификатора (команда → «Профили», задача и инициатива →
  «План квартала», инженер → «Звёздная карта», роль → «Роли и ёмкость», KPI → «KPI»).
* **Рекомендации.** Две независимые отметки: основание (`verified_by_scenario`, `proposal`,
  `needs_data`) и свежесть (`current`, `stale`, `superseded`). «Проверено» означает результат
  конкретного расчёта, а не вероятность успеха.
* **Новый прогон.** `newer_run_available` показывает предупреждение; кнопка «Обновить
  контекст» вызывает `POST …/context` с `expected_context_revision`.
* **Доказательства.** `GET /evidence/{id}`: тип (`snapshot`, `document`, `scenario`), ссылка и
  содержимое.
* **Сравнение мер** (роль `planner`). `POST …/scenarios/compare`: до 3 вариантов, в каждом до
  5 мер (`hire`, `loan`, `train`); результат — задание; опубликованный план не меняется.
* **Настройки** — вкладки «Модели», «Мои инструкции», «Проект и база знаний» (`admin`).
  Модели: список с проверкой (`POST /profiles/{id}/check`), добавлением по шаблону (Groq,
  OpenAI, Gemini, Ollama), правкой (`PUT /profiles/{id}`; пустая ссылка на ключ — прежняя) и
  удалением (`DELETE /profiles/{id}`) — для `admin`. Переключатель «Быстрые ответы без
  размышлений» сохраняет `capabilities.thinking=false`. Ключ задаётся ссылкой `env:ИМЯ` или
  `file:/путь`; инструкция «Как подключить свой ключ API» — на той же вкладке. Личные
  инструкции — `PUT /prompts/me`; проектный промпт и база знаний (`/kb/status`, `/kb/reindex`).
* Роль `viewer` пользуется чатами; без моделей отправка недоступна, экран подсказывает добавить
  модель (администратору — кнопкой).

### 2.3. Загрузка

1. Датасет — `POST /api/dataset` (роль `admin`); предупреждение, что прежние
   прогоны и факт будут стёрты.
2. Шаблон факта — `GET /api/actuals/template?sprint=N` с заголовком авторизации
   (ссылка `<a download>` заголовок не передаёт).
3. Факт спринта — `POST /api/actuals?sprint=N` (роль `planner`).
4. Новый PI или сценарий — `POST /api/pi-contexts` (роль `admin`): идентификатор
   PI, имя сценария, дата начала и Excel.

Тело запроса — **сам файл**, без multipart: `fetch(url, {method: 'POST', body: file})`;
имя файла передаётся в `?filename=`. Ответ `400` несёт `problems` — список проблем
по строкам; его **нужно показывать целиком**: это главный способ понять, что не
так с файлом.

История: таблица загруженных отчётов по факту (спринт, время, файл, выполнено,
в работе, часы, предупреждения) и архив исходных файлов — прежние версии не
пропадают, а получают статус «заменена версией №…».

### 2.4. План квартала

**`plan_task_schedule`** — расписание: `start_sprint` и `end_sprint` (пусты у
переносов — это не ошибка), `forecast_end_date`, `decision` (`in_quarter` или
`deferred_next_pi`; значение `cancelled` — только рекомендация), `reason_code`,
`reason_text` и `reason_details`. `reason_text` — готовое предложение по-русски,
показывается как есть; причина есть и у включённых задач.

**`v_plan_assignment_detail`** — «кем закрыто»: `engineer_id`, `hours`,
`home_team_id` и `serving_team_id` (разошлись — заём), `is_loan` (считает СУБД, не
пересчитывать), `served_role`, `native_role`, `is_substitution` (в штатном плане
всегда `false`, ADR-010).

**`plan_task_sp`** — доли Story Points по спринтам; их сумма равна остатку SP
задачи. Растянутая задача — одна полоса `start_sprint…end_sprint`; в карточке
показывать разбивку SP по спринтам, иначе «8 SP при ёмкости 7,2» выглядит ошибкой.

**`plan_baseline`** — базовая линия: **есть только у канонического базового
прогона** (`as_of_sprint = 0`), у пересчётов пуста — и это нормально. Базовую линию
и текущий план нельзя рисовать из одного запроса: это два запроса с разными
`run_id`, и в заголовке экрана это нужно подписать.

**`plan_dependency_bounds`** — допустимая нижняя граница старта задачи по
зависимостям.

Приоритет инициативы: в заголовке группы — число приоритета (серый — из датасета,
оранжевый — задан бизнесом) и кнопка правки для роли `planner`: число и обязательное
основание, «Снять» возвращает приоритет датасета. Сохранение
(`POST /api/initiatives/priority`) пересчитывает план и переключает экраны на новый
прогон; группы сортируются по действующему приоритету.

Подтверждение бизнес-результата (`POST /api/tasks/goal-confirmation`, роль
`planner`) показывается только для текущего прогона и для задач в `Done`.
**Цель и результат** (`v_plan_goal_outcome`) — четыре разных значения: цель
исполнителя, цель заказчика, предложение плана, подтверждённый результат.
Рекомендация отмены остаётся рекомендацией до подтверждения заказчика.

**Источники решения** — `GET /api/tasks/trace`: версия алгоритма, формулы, хэши
исходных файлов, спрос по ролям, назначения и ячейки Excel.

Сводка над ганттом: сколько задач в квартале, причины переноса и что делать.

### 2.5. Риски

**`alerts`** — три типа: `deadline_miss` (red), `role_deficit` (orange),
`cascade_shift` (yellow). `message` — готовый текст; `payload` — разбор по типу.

**`v_plan_diff`** — что изменилось между прогоном и предыдущим и почему (`cause`:
`own_slip`, `carry_over`, `dependency`, `capacity`, `completed`; `explanation` —
готовая фраза).

**`v_sprint_deviation`** — факт спринта против плана, действовавшего в нём: «в
срок», «не закрыта в срок», «раньше плана», плановые и фактические часы.

**`v_plan_violations`** — предупреждения приёмки; пусто — зелёная строка
«Предупреждений нет», а не пустое место и не доказательство выполнимости.

**Чувствительность** — `GET /api/scenarios/sensitivity` (только текущий прогон):
три детерминированных ухудшения входа; вероятности не оцениваются.

Фильтры на экране — клиентские (уровень, тип, спринт, поиск по задаче и тексту).

### 2.6. Звёздная карта

**`v_orbit_map`** — инженеры: `engineer_id`, `role_name`, `role_group`, `grade`,
`total_capacity_rate` (`"1.00"` или меньше у совместителей), `orbit_count`, `teams`,
`skills`, `bus_factor`, `risk`.

Раскладку считает фронт (`layout.ts`): ядра-команды по кругу, инженеры — спутники
по дуге; координат в данных нет, и раскладка детерминирована.

**Bus Factor по компетенциям** — `v_bus_factor_skill`: градация «критично»,
«предварительно: один носитель роли», «единственный носитель», «два носителя»,
«ок»; `demand_source` показывает, откуда спрос (`confirmed`, `role_proxy`,
`mixed`). Приближение через роль должно иметь видимую пометку. Покрытие ролей
(`v_role_coverage_org`: роли без людей в штате) — **отдельный блок**: это вопрос
найма, а не незаменимости.

**Панель инженера** — `v_engineer_absence_risk`: компетенции, где он единственный
носитель, и задачи текущего плана, которые встанут без него. Сценарий отсутствия
— `GET /api/scenarios/absence` (план перестраивается без публикации). Датированные
квалификации — `GET/POST /api/engineers/qualifications`; они **не дают права**
замещать роль.

**Панель команды** — клик по ядру: состав, ставки, роли, недостающие роли, живой
бэклог (`v_team_profile`) и список совместителей.

**`v_satellite_capacity`** — ёмкость по спринтам; `hours_own` уже умножен на
множитель спринта, пересчитывать нельзя.

### 2.7. KPI

`kpi_snapshots` отдаёт прогноз и факт для выбранного прогона. `kind` равен
`forecast` или `actual`; показываются **рядом**, а не вместо друг друга. Строки
`say_do_ratio` относятся к спринтам; `pi_predictability` и `bus_factor` — к
кварталу. Значение может быть `null`: показывать `N/A` и `calculation_status`
(`no_commitment`, `no_plan`, `no_relevant_skills`), а не 0 или 100. Нормы — из
`target_min` и `target_max` строки; `null` у верхней границы значит «без
верхней границы».

* Рядом с процентом выполнения квартала всегда строка охвата: «обещано N из M
  инициатив, частично K, не обещано L».
* Промежуточный факт рисуется нейтрально и сравнивается с плановым накоплением
  («к концу спринта k по плану завершено X, завершено Y»); итоговая норма
  применяется к итогу квартала.
* «Выполнение плана спринта» показывает два разных числа: «план завершений» (SP
  задач, которые база закрывает в спринте) и «бюджет работ» (доли SP текущего
  плана); у закрытых спринтов — «Перед спринтом ждали X SP» из
  `v_sprint_forecast_accuracy`.
* Качество плана — `GET /api/plan-quality`: подтверждённая ценность, частичные
  инициативы, ожидание зависимостей, перенос обещанного, смены исполнителей и
  сравнение режимов `greedy` и `atomic`.

### 2.8. Роли и ёмкость

Четыре разные вещи, их нельзя путать.

1. **Дефицит «команда × роль»** — `v_role_deficit`: `demand_hh`, `supply_hh`,
   `gap_hh`, `verdict`. `gap_hh` **отрицательный, когда потребность покрыта**:
   знак читать строкой. Рядом показывать `v_role_deficit_effective` (с учётом
   замещения): сейчас значения совпадают, и они разойдутся, если замещения
   разрешат.
2. **Где нужен наём** — `v_role_coverage_org`: `native_people`,
   `people_incl_substitution`, `supply_hh`, `gap_hh`, `verdict`.
3. **Незаменимость по ролям** — `v_bus_factor`: `bus_factor`, `demand_hh`, `risk`.
4. **Ёмкость команды** — `v_team_capacity_sp` и `teams` (`focus_factor`).

Кадровые меры — `GET /api/scenarios/workforce` (наём, обучение, перевод 0,5 ставки;
гипотезы, штатный план не меняют). Разметка стека задач —
`GET/POST /api/tasks/skill-review`: подтверждение пересчитывает план. Качество
исходных данных — `v_dq_summary` и рабочий список находок с решениями
(`POST /api/dq-issues/review`).

Пустое состояние «В команде нет строк по этой роли» — это и есть вердикт «роли нет в
команде», а не ошибка.

### 2.9. Профили

Карточка команды подписывает величины однозначно: «Velocity (история)» и «SP / PI
(история)» — нормативные; «SP / спринт (прогон)» — ёмкость выбранного прогона из
`plan_team_capacity`. Под ними строка основания: «Ёмкость по N наблюдениям (история
H, факт текущего квартала F), разброс истории ±σ SP»; оранжевое предупреждение, если
последнее наблюдение истории старше 90 дней до PI или наблюдений меньше трёх.
Плашка «Совместители» раскрывается списком людей с ролью, ставкой и командами.

### 2.10. Данные

Весь журнал находок (`v_dq_issue_worklist`) с фильтрами по серьёзности, правилу и
тексту. Выгрузка текущей выборки в CSV, XLSX и JSON выполняется в браузере.

## 3. Вход и роли

Сервер требует токен (ADR-027). Первый запрос фронта — `GET /api/me`:

* `401` — экран входа (одно поле «Токен доступа»); неверный токен — «Токен не
  подошёл», `429` — «Слишком много неверных попыток. Подождите минуту»;
* `200` — приложение открывается; в шапке имя, роль плашкой и кнопка выхода,
  которая очищает токен и кэш данных;
* любой другой запрос, получивший `401` (токен отозвали), возвращает на экран входа.

Маршруты записи и роли:

| Роль | Маршруты |
|---|---|
| `admin` | `POST /api/dataset`, `POST /api/pi-contexts` |
| `planner` | `POST /api/actuals`, `/api/actuals/role-review`, `/api/tasks/goal-confirmation`, `/api/tasks/skill-review`, `/api/engineers/availability`, `/api/engineers/qualifications`, `/api/initiatives/priority`, `/api/dq-issues/review`, `/api/planner/compare` |
| `viewer` | все `GET` (кроме публичных `livez`, `health`, `version`) |

Роль ограничивает действия, а не экраны: `viewer` на экране «Загрузка» видит
пояснение «Режим просмотра». При отключённой авторизации (`auth: "off"`) экран
входа и плашка пользователя не показываются, а подтверждающего результат вводят
вручную. Контекст PI и сценария выбирается заголовками `X-PI-ID` и `X-Scenario-ID`.

## 4. Чего фронт не делает сам

Каждый пункт уже был причиной расхождения цифр между экранами.

| Нельзя | Делать так |
|---|---|
| Считать фонд квартала арифметикой в коде | брать `v_pi_fund_factor.factor` и `v_sprint_fund_factor.factor` |
| Зашивать число спринтов | читать `sprints` |
| Зашивать нормы KPI | красить по `target_min` и `target_max` из `kpi_snapshots` |
| Пересчитывать `is_loan`, `is_substitution`, `is_native` | брать флаги из `v_plan_assignment_detail` и `v_engineer_role_coverage` |
| Считать календарную длительность суммой часов ролей | сумму часов считать трудозатратами, длительность брать из расписания |
| Выводить знаменатель KPI из `tasks.committed_week0` | брать `plan_baseline` канонического прогона |
| Брать `plan_baseline` из прогона по умолчанию | запрашивать его с `run_id` канонического базового прогона |
| Вычислять «текущий прогон» самому | не передавать `run_id`: сервер подставит `run_default: true` |
| Зашивать в код пороги окраски плиток KPI | брать границы нормы из строки KPI |
| Кэшировать ответы дольше жизни вкладки | `Cache-Control: no-store` уже стоит |

## 5. Что нужно объяснить словами

Данные честные, но выглядят «как ошибка», если не подписать.

* **`PLANNED_END_OVERSAIL` (предупреждение).** Прогноз окончания позже `planned_end`
  из исходного файла. Это не срыв: даты в исходнике — история, план по ним не
  строился (ADR-016). «Прогноз позже исходного срока; срок в исходнике — факт
  истории, а не обещание».
* **Алерты по ролям.** «Роль «Аналитик 1С»: нужно N ЧЧ, доступно 0 ЧЧ». Это
  следствие запрета замещать роли (ADR-010), а не дефект плана. «Влияет на план
  только через наём или дообучение».
* **Красные KPI.** Предсказуемость считается по обещанным инициативам, а в квартал
  попадает не весь бэклог; Bus Factor — минимум по востребованным компетенциям, и
  роли без людей в штате его обнуляют. «Показатель по определению жёсткий;
  смотреть вместе с числом задач в квартале и списком ролей без людей».
* **Приближённый стек.** Для неразмеченных задач совпадение стека не доказано;
  Bus Factor по ним — оценка через роль, и это должно быть видно.

## 6. Скорость

* Витрины вычисляются из вложенных вьюх: время ответа не зависит от числа строк.
  Если экран делает несколько запросов сразу, показывать скелетон, а не белый экран.
* Справочник `GET /api/views` можно запрашивать один раз при старте, но не кэшировать
  дольше сессии: состав витрин — часть контракта.
* Первый запрос после запуска сервера может занять секунды. Таймаут на стороне
  фронта — не меньше 30 с.
* Пагинация нужна «по смыслу», а не ради скорости; серверные фильтры не нужны:
  данные фильтруются в браузере.
