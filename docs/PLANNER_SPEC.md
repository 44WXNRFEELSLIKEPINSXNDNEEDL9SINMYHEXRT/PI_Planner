Планировать нужно **37 задач** со статусом `ToDo` и `InProgress`.
Задачи `Done` не трогать: они уже в истории и нужны только как предшественники.

### Ловушка №1: остаток по InProgress

У шести задач `InProgress` колонка `tasks.spent_time` **пуста**. Факт лежит
только в `task_role_spent`. Не считайте остаток как `estimated_hh - spent_time` —
получите полную оценку вместо остатка. Берите `v_task_remaining_hh`, там уже
`GREATEST(смета - факт, 0)` по каждой роли.

### Ловушка №2: три источника часов

`tasks` несёт три колонки с трудозатратами, и они расходятся у **25 из 45**
задач. Использовать **только** `estimated_hh_effective` (⚠ ADR-002). Остальные
две — для отчёта о качестве данных.

### 1.1. Календарь PI и фонд часов (ADR-007, ADR-017)

Квартал: **01.07.2026–22.09.2026, 84 дня** — начало календарного квартала плюс
6 × 14 дней (ADR-025). Спринты идут по 14 дней
от начала, поэтому 92 = 6 × 14 + 8 и **последний спринт короче — 23.09–30.09,
8 дней**. Длина спринта — не косметика: фонд часов пропорционален ей.

```
фонд спринта   = ставка × fte_hours_per_sprint × v_sprint_fund_factor.factor
фонд квартала  = ставка × fte_hours_per_sprint × v_pi_fund_factor.factor
```

Множители живут только в этих двух вьюхах (сейчас 1.0000 и 6.0000):
в коротком спринте команда получает 45.712 ЧЧ на ставку вместо 80, за квартал —
480 ЧЧ на ставку за квартал. Границы PI уезжают в прогон:
`plan_runs.params.calendar` = `{pi_start, pi_end, sprint_count, pi_days,
fund_factor, fund_hh_per_fte, short_sprints}`.

Планировщик читает множитель из БД (`v_sprint_fund_factor`, `v_pi_fund_factor`),
а не считает «92 / 14» у себя: иначе его фонд разъедется с инвариантами.

## 2. Четыре ограничения

### A. Ёмкость команды в Story Points

```
Σ SP задач команды T, начатых в спринте S
    ≤  v_team_capacity_sp.available_sp_per_sprint(T) × v_sprint_fund_factor(S)
```

**Конвенция (ADR-016):** SP задачи засчитываются **один раз**, в её
`start_sprint`. Если задача растянута на несколько спринтов, SP не размазываются.
Изменится конвенция — правится инвариант `SP_OVERFLOW`.

Два следствия, принятые явно:

* задача, у которой `estimation_sp` больше ёмкости команды за спринт, не
  поместится **никогда**, даже если часов хватает на два спринта. Это
  бизнес-ограничение, а не дефект алгоритма: такая задача уезжает
  в `deferred_next_pi`;
* у задач `InProgress` берётся **остаток часов**, но **полный SP**. Повторно SP
  не списывается: он засчитывается в спринте старта того прогона, в котором
  считается, а `SP_OVERFLOW` работает в пределах прогона.

Ёмкость = средний исторический velocity × 0.8. Уже посчитана, Focus Factor
применён. Ёмкость спринта умножается на его factor — иначе в
последние 8 дней квартала планировалось бы столько же, сколько в полные 14.

### B. Часы инженера

```
Σ hours(инженер E, спринт S)  ≤  E.total_capacity_rate × 80 × factor(S)
```

Проверяется по **сумме всех орбит**: `ENG-419` на 0.5+0.5 даёт 80 ЧЧ за спринт
суммарно, а не 80 на каждую команду. Это главная ошибка, которую легко сделать.

**Бюджет орбиты — отдельный жёсткий потолок** (ADR-015):

```
Σ hours(инженер E, орбита T, спринт S)  ≤  E.capacity_rate(T) × 80 × factor(S)
```

Сумма ставок равна `total_capacity_rate`, поэтому перекос «списали 80 ЧЧ
с орбиты, у которой бюджет 40» проверкой по сумме **не виден** — его ловит
`ORBIT_OVER_BUDGET`.

**Одна строка `plan_assignments` = одна орбита.** `home_team_id` не входит
в первичный ключ `(run_id, task_id, sprint_no, engineer_id, role_id)`, поэтому
разложить одно назначение по двум орбитам нельзя: остаток часов берёт следующий
кандидат или следующий спринт. Так отчётность по орбитам совпадает с фактом.

### C. Роль и стек

Назначение `(engineer_id, role_id)` допустимо, только если такая пара есть в
`v_engineer_role_coverage`. Там уже сведены:

* родная роль инженера (`is_native = true`);
* разрешённые замещения (`is_native = false`), с проверкой `min_grade` и
  исключением строк со `status = 'rejected'`.

**Замещения отклонены организаторами** (ответ №2, ADR-010), поэтому алгоритм
фильтрует `WHERE is_native` и работает строго: в штате нет 6 ролей со спросом
665 ЧЧ. По ролям проходят 11 задач из 37, а с учётом часов и SP-ёмкости
планировщик ставит 7 — разница разобрана в приёмке M2 (`docs/RUNBOOK.md`, раздел 9).

**Кандидаты на роль берутся из этой же вьюхи** (ADR-012), а не из
`engineers.role_id`: вьюха — единственный источник правды о паре
«инженер × роль», и при включении дообучения менять код не придётся.

**`efficiency`** (множитель часов) применяется к потребности: чтобы закрыть смету
`remaining_hours`, исполнителю нужно `remaining_hours × efficiency` **своих**
часов (ADR-016). Сейчас во вьюхе везде `1.00`, поэтому часы совпадают со сметой.

`v_role_coverage_org` зачисляет фонд универсального инженера каждой доступной ему
роли, поэтому её цифры (665 ЧЧ найма, 132 ЧЧ по 1С-ролям) — **срез спроса против
родного фонда**, а не вердикт по расписанию: вердикт даёт сам план.

Связи «задача → конкретные технологии» в датасете **нет** — есть только
«задача → роль → часы». Матчинг идёт по роли. Если появится
`task_skill_requirements`, добавится ещё одно условие.

### D. Зависимости (ADR-013)

Тип зависимости — **явный параметр прогона** `dependency_mode`:

```
start_start (по умолчанию):  start(blocked)  ≥  start(blocking) + min_gap_sprints
finish_start:                start(blocked)  ≥  end(blocking)   + min_gap_sprints
```

`min_gap_sprints = 1` (⚠ ADR-003). По умолчанию — `start_start`: именно эту
семантику реализует предпосчитанный `task_sequence.earliest_start_sprint`
(у `MOB-7012` и `MP-103` он равен 2 при блокирующих с `earliest = 1`), и заново
топологию считать не нужно. На текущем сиде оба режима дают одинаковый план —
но правило теперь **выбрано**, а не подразумевается.

**Перенесённая блокирующая тянет зависимую за собой:** задача не может быть
в квартале, если её блокирующая уехала в следующий PI. Проверка
`DEPENDENCY_BLOCKER_DEFERRED` ловит это независимо от алгоритма: раньше
`DEPENDENCY_VIOLATED` смотрел только пару «обе в квартале» и пропускал цепочку
`SRV-4091 → SRV-4092`.

**Важно:** живых рёбер всего **10 из 19** (остальные висят на задачах `Done`),
**27 из 37** задач вообще не имеют предшественников, максимальная глубина
цепочки — **2**. Зависимости здесь почти ничего не ограничивают. Узкое место —
ресурсы.

## 3. Механика назначений

### Распределение часов (ADR-015)

Правила, по которым часы ложатся в спринты. Слово «хватает» из псевдокода
раскрыто здесь:

* **роли параллельны.** Внутри одного спринта цикл идёт по ролям, и каждая берёт
  столько часов, сколько дают свободные исполнители; роли друг друга не ждут;
* **одну роль могут закрывать несколько человек** в одном спринте — на каждого
  пишется своя строка `plan_assignments`;
* **часы роли переезжают в следующий спринт**, если в текущем их не хватило:
  задача растягивается (`end_sprint > start_sprint`);
* **окно задачи** — `[min, max]` фактически использованных спринтов. Разрывы
  внутри окна разрешены (задача ждёт конкретную роль) и видны как warning
  `WINDOW_HAS_GAP`;
* **пробные назначения откатываются.** Не нашлось часов до конца квартала —
  `funds.free()` возвращает в фонд всё, что задача успела занять, и задача уходит
  в перенос;
* **порядок кандидатов детерминирован:** сначала инженеры со своей орбитой (по
  убыванию свободных часов орбиты), затем заёмщики (по убыванию общего остатка),
  при равенстве — по `engineer_id`. Без этого один и тот же вход давал бы разные
  планы;
* **резервирования своей ёмкости нет.** Бюджет орбиты не бронируется заранее, но
  свои задачи получают приоритет порядком кандидатов, а бюджет орбиты — жёсткий
  потолок (`ORBIT_OVER_BUDGET`).

**Известное ограничение.** Жадный алгоритм не переставляет уже принятые
назначения, поэтому случай «универсал занят ролью A, а роль B больше закрыть
некому» в общем виде не решается: его ограничивают порядок обхода, «своя орбита
первым» и атомарный режим инициатив. Полное решение — MILP (ADR-011).

### Орбиты и займы (⚠ ADR-001)

Инженер привязан к команде через `engineer_orbits` со ставкой. Порядок выдачи
часов:

1. сначала закрываются задачи **своих** команд по `capacity_rate`;
2. невыбранный остаток доступен **чужим** командам как заём.

В `plan_assignments` пишутся оба поля:

* `home_team_id` — орбита, с которой сняты часы (должна быть в
  `engineer_orbits` этого инженера);
* `serving_team_id` — команда, которой принадлежит задача (`tasks.team_id`).

`is_loan` считает СУБД сама, писать не надо.

**Без займов план нерешаем:** 2371 ЧЧ дефицита по 47 связкам «команда × роль»,
и все 47 — вида «роли вообще нет в команде».

### 3.5. Пересчёт в середине квартала (ADR-014)

`as_of_sprint = k` — пересчёт на начало спринта `k` (0 — базовый план Недели 0).

| Правило | Как именно |
|---|---|
| Прошлое неприкосновенно | `replan_floor = max(1, k)`: планируются спринты `k..7`. Проверка `ASSIGNMENT_IN_CLOSED_SPRINT` |
| Прогон аддитивен | новый `run_id`; старые расписания остаются историей, `plan_baseline` пишется один раз (проверки `BASELINE_ON_REPLAN`, `BASELINE_MUTATED`) |
| Факт по ролям | `v_task_remaining_hh` = `GREATEST(смета − факт, 0)` по каждой роли из `task_role_spent`. `tasks.spent_time` для этого не годится (ловушка №1), `task_state` — тоже |
| `task_state` | это **витрина для фронта**, а не источник остатка: разбивки по ролям в ней нет. Проверка `STATE_SNAPSHOT_INCOMPLETE` следит за полнотой слепка |
| Начатые и завершённые задачи | вход — `status IN ('ToDo','InProgress')`; `Done` не планируется; задача с нулевым остатком получает символическое назначение `0.01` ЧЧ |
| Ёмкость | бюджеты спринтов от `k` до конца квартала, каждый × свой factor |
| Обещание Недели 0 | из расписания **канонического** прогона: `MIN(run_id)` среди удачных с `as_of_sprint = 0` |

**Ограничение.** Фактических часов **по спринтам** в датасете нет
(`task_role_spent` — итог по задаче и роли), поэтому часы, уже потраченные
в текущем спринте, не вычитаются.

### Что записывать

| Таблица | Когда |
|---|---|
| `plan_runs` | одна строка на прогон; `as_of_sprint = 0` — базовый план. В `params` едут режимы и **календарь** (`params.calendar`: границы PI, дни, `fund_factor`, короткие спринты) |
| `plan_baseline` | **только** при `as_of_sprint = 0`, дальше не меняется |
| `plan_task_schedule` | одна строка на каждую планируемую задачу |
| `plan_assignments` | по строке на (задача, спринт, инженер, роль) |
| `task_state` | слепок каждой задачи на этот `as_of_sprint` |
| `alerts` | все сработавшие риски |
| `kpi_snapshots` | три KPI |

## 4. Порядок обхода и решения

```
1. отсортировать инициативы по initiatives.priority_rung DESC        (⚠ ADR-005: MAX(rung))
2. внутри инициативы — задачи по task_sequence.topo_order ASC
3. для каждой задачи найти минимальный спринт S, где одновременно:
      S >= max(as_of_sprint, task_sequence.earliest_start_sprint)
      S >= готовая_граница(предшественника) + min_gap_sprints
      хватает SP у команды в S
      хватает часов у исполнителей по каждой требуемой роли
4. нашли  -> decision = 'in_quarter', записать назначения
   не нашли до 7-го спринта -> decision = 'deferred_next_pi'
```

`готовая_граница` — `start` блокирующей при `dependency_mode = start_start`
и `end` блокирующей при `finish_start` (§2D).

### Целевая функция (ADR-015)

Порядок обхода — это и есть цель, и она записана в каждый прогон:

```
objective = lexicographic: initiatives.priority_rung DESC,
            task_sequence.topo_order ASC, start_sprint ASC
```

* приоритет инициативы важнее всего, внутри инициативы — топология, и только
  потом «поставить как можно раньше»;
* перестановок и повторного поиска нет: `deferred_next_pi` значит «не влезло при
  уже принятых назначениях», а не «невыполнимо в принципе». Это сказано и в
  `params.objective_note`;
* цена выбора видна числами: `params.initiatives_complete` и
  `params.initiatives_partial`.

### Атомарность инициативы (ADR-013)

`initiative_mode`:

* `greedy` (**по умолчанию**) — задача решается отдельно, частичная инициатива
  допустима;
* `atomic` — пробная упаковка инициативы целиком: не влезла хоть одна задача,
  все уже поставленные снимаются (`release_initiative`), их SP и часы
  возвращаются в фонд, инициатива уходит в перенос целиком.

Замер на живых данных: `greedy` — 7 задач и 1 инициатива из 15 целиком;
`atomic` — 2 задачи и та же одна инициатива. `pi_predictability` в обоих режимах
6.67, поэтому по умолчанию выбран `greedy` (ADR-013).

Задача может растягиваться на несколько спринтов, если часы одной роли не
помещаются в один: `end_sprint > start_sprint`.

### Коды решений

| `decision` | Когда | `decision_reason` |
|---|---|---|
| `in_quarter` | влезла целиком | `NULL` |
| `deferred_next_pi` | не хватило ресурсов или времени | `M2` «Отсутствие ресурсов» |
| `cancelled` | снята заказчиком | код из `ref_mismatch_reasons` |

Инициатива считается выполненной, только если **все** её задачи получили
`in_quarter`. Это же определение используется в KPI.

## 5. Алерты

| Уровень | Тип | Условие |
|---|---|---|
| `red` | `deadline_miss` | прогноз завершения выходит за квартал → срыв инициативы `PRODF` |
| `yellow` | `cascade_shift` | задача сдвинулась и потянула за собой зависимые, дедлайн пока цел |
| `orange` | `role_deficit` | потребность по роли на спринт > фонда доступных часов |

Отдельно обязательны оранжевые алерты по ролям из `v_role_coverage_org` с
вердиктом `НАЙМ`: **665 ЧЧ на 6 ролях** — РП 449 ЧЧ, поддержка 84 ЧЧ и 132 ЧЧ на
четырёх 1С-ролях (задачи `SRV-4043`, `SRV-4091`, `MOB-7013`). Замещения
отклонены организаторами (ответ №2, ADR-010), поэтому закрыть эти часы нечем:
1С-задачи получают оранжевый алерт, `deferred_next_pi` и
`decision_reason = 'M2'`, в `details` — роль, часы и список задач. Текст —
«нужен наём или дообучение», это вывод для заказчика, а не сбой.

**Выход за даты исходного плана алертом не является.** `tasks.planned_start` /
`planned_end` — исторический план, а не обязательство (ADR-016), поэтому прогноз
сравнивается с концом PI (red `deadline_miss`), а выход за `planned_end` виден как
warning приёмки `PLANNED_END_OVERSAIL`: показать в UI, но не блокировать.

## 6. KPI

| Код | Формула | Норма |
|---|---|---|
| `pi_predictability` | завершённых `PRODF` / запланированных на Неделе 0 × 100 | 80–100 |
| `say_do_ratio` | сделано SP в спринте / запланировано SP на спринт × 100 | 90–105 |
| `bus_factor` | минимум по ролям со спросом, разбивка в `details` | > 1 |

**Bus Factor — по ролям, не по технологиям.** Связи «задача → технология»
в датасете нет, есть «задача → роль → часы», поэтому `v_bus_factor` считает людей
по родным ролям. В `details` едут разбивка по ролям и список `critical`
(`bus_factor ≤ 1`). Появится `task_skill_requirements` — показатель получит
технологическое измерение.

**Правила, без которых KPI не посчитать** (ревью M2, пункт 9):

* **канонический базовый прогон** — первый удачный с `as_of_sprint = 0`:
  `MIN(run_id) WHERE as_of_sprint = 0 AND status = 'ok'`. Тот же предикат стоит
  в проверке `BASELINE_MUTATED`, поэтому код и приёмка не могут разойтись;
* **номер спринта** берётся не из `plan_baseline` (там его нет), а из расписания
  канонического прогона — `plan_task_schedule`;
* **нулевой знаменатель**: `say_do_ratio` → 100.00 («нечего было обещать —
  нечего проваливать»), `pi_predictability` → 0 (живых задач нет, показатель
  не определён);
* **сравнивается план с планом**: факта по будущим спринтам нет, поэтому
  «сделано» = «стартовало в обещанном спринте в текущем прогоне»;
* **ранее завершённые инициативы не мешают**: на вход планировщику идут только
  `ToDo`/`InProgress`, поэтому `Done` не попадает ни в числитель, ни
  в знаменатель;
* знаменатель берётся из `plan_baseline` и расписания базового прогона, а **не**
  из `tasks.committed_week0`: в исходнике колонка заполнена только у 8 задач
  `Done` (⚠ ADR-004);
* проверка `KPI_INCOMPLETE` следит, что за прогон посчитаны ровно 1
  `pi_predictability`, `sprint_count` строк `say_do_ratio` и 1 `bus_factor`,
  без NULL-значений.

Пороги писать в `target_min` / `target_max` — фронт красит плашку по ним.

## 7. Приёмка

После каждого прогона:

```sql
SELECT * FROM v_plan_violations WHERE run_id = :run_id;                    -- всё
SELECT * FROM v_plan_violations WHERE run_id = :run_id AND severity = 'error';  -- приёмка
```

**Критерий приёмки: нет строк с `severity = 'error'`.** Строки
`severity = 'warning'` план не отменяют, но обязаны быть показаны в UI: это
замещение роли, выход за даты исходного плана и разрыв в окне задачи. Раньше
формулировка «пустой результат = план корректен» противоречила самой же проверке
`SUBSTITUTION_USED` с её `warning` (ревью M2, пункт 4).

**Приёмка проверяет корректность, а не оптимальность.** «Нет ошибок» не значит
«план лучший из возможных»: качество видно в KPI и алертах. Это сказано и здесь,
и в `COMMENT ON VIEW v_plan_violations`.

Проверок **29** (A…AC) в `db/05_invariants.sql`:

| Код | Severity | Что проверяет |
|---|---|---|
| `SP_OVERFLOW` | error | SP команды в спринте старта ≤ `available_sp_per_sprint` × factor спринта |
| `ENGINEER_OVERLOAD` | error | часы инженера в спринте ≤ ставка × 80 × factor спринта (сумма всех орбит) |
| `ORBIT_OVER_BUDGET` | error | часы с орбиты в спринте ≤ `capacity_rate` × 80 × factor спринта |
| `ROLE_NOT_COVERED` | error | пара «инженер × роль» есть в `v_engineer_role_coverage` |
| `HOME_TEAM_NOT_ORBIT` | error | орбита списания есть в `engineer_orbits` |
| `SERVING_TEAM_MISMATCH` | error | `serving_team_id` = владелец задачи |
| `ASSIGNMENT_OUTSIDE_WINDOW` | error | назначение внутри `start..end` задачи |
| `WINDOW_OUTSIDE_PI` | error | окно задачи внутри квартала |
| `SPRINT_OUT_OF_PI` | error | номер спринта ≤ `sprint_count` |
| `ASSIGNMENT_IN_CLOSED_SPRINT` | error | пересчёт не пишет в прошлые спринты |
| `DEPENDENCY_VIOLATED` | error | зазор между зависимыми (по `dependency_mode`) |
| `DEPENDENCY_BLOCKER_DEFERRED` | error | перенесённая блокирующая не оставляет потомка |
| `START_BEFORE_EARLIEST` | error | старт не раньше `task_sequence.earliest_start_sprint` |
| `UNDER_ALLOCATED` | error | часов по роли назначено не меньше остатка сметы |
| `IN_QUARTER_WITHOUT_ASSIGNMENTS` | error | у `in_quarter` есть назначения |
| `DEFERRED_WITH_ASSIGNMENTS` | error | у перенесённой нет назначений |
| `DEFERRED_WITHOUT_REASON` | error | у переноса есть `decision_reason` |
| `DONE_TASK_SCHEDULED` | error | `Done` не планируется |
| `TASK_MISSING_FROM_PLAN` | error | на каждую живую задачу есть решение |
| `BASELINE_MISSING` | error | базовый прогон пишет `plan_baseline` |
| `BASELINE_INCOMPLETE` | error | база покрывает все живые задачи и без нулевых SP |
| `BASELINE_ON_REPLAN` | error | пересчёт не пишет базу |
| `BASELINE_MUTATED` | error | база не расходится с каноническим прогоном |
| `KPI_INCOMPLETE` | error | 1 + `sprint_count` + 1 KPI, без NULL |
| `STATE_SNAPSHOT_INCOMPLETE` | error | `task_state` — все задачи и свой `as_of_sprint` |
| `ALERTS_MISSING` | error | при переносах есть хотя бы один алерт |
| `SUBSTITUTION_USED` | warning | использовано замещение роли |
| `PLANNED_END_OVERSAIL` | warning | прогноз выходит за даты исходного плана |
| `WINDOW_HAS_GAP` | warning | в окне задачи есть спринт без назначений |

**Негативный тест.** Проверки, которые ничего не находят, ничего и не доказывают.
Поэтому в `tools/negative_test.sql` живёт синтетический «плохой» прогон внутри
транзакции с `ROLLBACK`: 56 нарушений, 14 разных кодов, следов в базе не
остаётся. Прогон и разбор — `docs/RUNBOOK.md`, раздел 9. Разбор ревью M2 —
`docs/REVIEW_RESPONSE.md`.

## 8. Что изменилось после сверки с ТЗ

Раздел дополняет правила выше; при расхождении верен он.

### 8.1. Story Points текут по спринтам (ADR-020)

SP задачи больше **не** списываются целиком в спринт старта. Команда в каждом
спринте берёт столько SP, сколько у неё свободно, остаток идёт дальше; доли —
в `plan_task_sp`, их сумма равна `estimation_sp` задачи (инвариант
`SP_SHARES_MISMATCH`). Окно задачи — до последнего спринта с часами **или** с SP.

Почему: при прежнем правиле задача, у которой SP больше ёмкости команды за
спринт, не попадала в план никогда. Таких живых задач пять, и среди них
`DB-202` — та самая, которую онбординг приводит как пример растягивания на два
спринта.

### 8.2. Повторная упаковка (проход 4)

Переносы проходов 2–3 возвращают часы и SP в фонд. После них планировщик ещё раз
пробует разместить перенесённые задачи, у которых нет ни отсутствующих ролей, ни
перенесённых блокирующих. Без этого прохода освободившийся ресурс пропадал, а
причина «не хватило ресурсов» была бы неправдой.

### 8.3. Причина у каждого решения (ADR-022)

`reason_code` + `reason_text` + `reason_details` заполняются у **всех** строк
расписания, включая включённые задачи. Коды — в `ref_decision_reasons`.
Старая колонка `decision_reason` (`M2`/`M3`/`M4`) сохранена для совместимости.
Решение без объяснения — ошибка приёмки (`DECISION_WITHOUT_EXPLANATION`).

Отмена (`cancelled`) назначается только после пробной раскладки задачи в
«следующий квартал» с тем же штатом. Роли, которых нет в штате, в эту симуляцию
не попадают: такие работы переносятся, а закрываются наймом или дообучением.

### 8.4. KPI: прогноз и факт (ADR-023)

`kpi_snapshots.kind` = `forecast` | `actual`. Знаменатель «процента выполнения
квартала» — инициативы, **все** живые задачи которых стояли в квартале в
первоначальном плане. «Выполнение плана спринта» сравнивает SP, закрытые по
факту в спринте, с SP, которые первоначальный план на этот спринт назначал.

Bus Factor считается по компетенциям (`v_bus_factor_skill`), норма — «> 1», то
есть `target_min = 2`.

### 8.5. Факт спринтов (ADR-021)

Планировщик факт **не читает напрямую**: загрузка обновляет состояние задач
(`apply_actuals()`), а планировщик, как и раньше, читает витрины. Новое во входе:
`last_reported_sprint`, `done_in_sprint`, `baseline_schedule`, `actuals_upload_id`
— они нужны только для KPI и алертов.

`as_of_sprint = sprint_count + 1` — итоговый прогон квартала: планировать некуда,
все живые задачи уходят в следующий PI с причиной `PI_CLOSED`, статус прогона
остаётся `ok`.

### 8.6. Оранжевый алерт — про следующий спринт

«Дефицит специалистов **на следующий спринт**»: потребность роли на спринт,
который начинается сейчас (часы, уже поставленные на него, плюс остаток задач,
которые могли бы в нём стартовать, но не получили специалиста), сравнивается с
фондом этой роли в спринте. Квартальный дефицит по ролям виден отдельно —
`v_role_coverage_org`.
