# Change log алгоритмов планирования

Журнал ведётся по фактически выполненной работе над `lns-cpsat@1`.
Новые записи добавляются сверху. Дата ниже — дата рабочей среды.

## 2026-10-07 — усиление модели и реализация предложений INFO

Модель (`solver.py`):
- Избыточные отсечения, не меняющие множество решений: ёмкость спринта для
  задачи по квалифицированным людям, минимальная длительность, линейные формы
  окна задачи, рюкзаки роли и SP команды на весь PI.
- Индикаторы `running[t,k]` («у задачи есть работа в спринте k или позже»)
  и энергетические отсечения: работа задач, завершённых к спринту k, обязана
  уместиться в фонд спринтов 1..k (по роли и по SP команды). Разрыв между
  значением и границей суммы спринтов завершения сократился примерно с 65%
  до 17–24%.
- Доля SP задаётся линейной полосой floor/ceil вместо `AddDivisionEquality`.
- Новые уровни цели после всех критериев поставки: «дыры» в окне задачи,
  число исполнителей на задачу-роль, число строк назначений. Независимый
  оценщик считает их так же.
- Если уровню не хватило времени, но решение уже есть, его значение
  сохраняется и оптимизация переходит к следующему уровню.

LNS по INFO:
- П. 3: задачи вне окрестности входят в модель константами (их часы и SP
  вычтены из фондов). Окрестность из одной задачи — 0.1 с вместо 0.7 с
  на 40 задачах; вектор модели совпадает с независимым оценщиком.
- П. 1: окрестность «конфликт» — отложенная задача (с уклоном в высокий
  приоритет), её отложенные предшественники и задачи, занявшие подходящих
  людей или SP её команды в доступных спринтах.
- П. 2: любая окрестность, включая детерминированную, замыкается до целых
  инициатив и отложенных предшественников.
- П. 4: вместо остановки после серии неудач освобождаются все задачи; точное
  решение без улучшения доказывает оптимум и останавливает поиск, иначе
  размер окрестности сбрасывается. Доля начальной полной модели (0.5)
  проверена против 0.2/0.35/0.7 и оставлена.
- П. 5: `optimization.neighborhood_log` — тип и размер окрестности, время,
  статус, первый изменившийся уровень, прирост и границы.

Проверка на синтетике, локально, 1 поток:

- Тесты: 339 passed, 20 skipped.

## 2026-10-07 — гарантия «не хуже Greedy» и адаптивный LNS

- Greedy-план мог не проходить валидатор LNS (копеечные фрагменты: часы
  0.00 при работе > 0, расхождение суммы работы на 0.0001). Тогда seed молча
  отбрасывался и CP-SAT стартовал без начального решения: на синтетике из
  100 задач LNS выдавал план хуже Greedy. Теперь вектор Greedy всегда служит
  лексикографической нижней границей, невалидный план используется как hint,
  а итог, лексикографически худший Greedy, не публикуется: возвращается
  Greedy с `fallback_reason`.
- Нижняя граница уровня применяется, только пока все более ранние уровни
  равны эталону. Раньше улучшение верхнего уровня могло сделать нижний
  невыполнимым и обрывало оптимизацию.
- Время делится между уровнями цели, константные уровни не решаются. Раньше
  первый уровень мог съесть весь бюджет.
- LNS работает до исчерпания бюджета, а не до 32 попыток. Детерминированные
  операторы чередуются со случайными структурными окрестностями (команда,
  исполнитель, окно спринтов, смешанная) адаптивного размера; инициативы
  освобождаются целиком.
- Настройка `PLANNER_SEARCH_WORKERS` (по умолчанию 1) задаёт число потоков
  CP-SAT для начального решения.
- Локальная синтетика, 1 поток: 40 задач/20 с — 6/6 лучше Greedy, сумма
  спринтов завершения на 12–27 меньше прежней версии LNS; 100 задач/40 с —
  4/4 лучше Greedy, прежде 1 из 3 был хуже. Тесты: 337 passed, 20 skipped.

## 2026-10-07 — сохранение качества плана и исправление критерия stability

- `DB-202` выпадала из-за жёсткой формулы stability: требование половины
  общего объёма задачи было применено к каждому исполнителю, хотя решение
  должно лишь штрафовать за слабое сохранение прежних исполнителей. Теперь
  штраф считается по суммарной прежней группе отдельно для каждой роли;
  само распределение остаётся допустимым при любом объёме.
- LNS получает проверенный Greedy-план как начальный incumbent. Каждый уровень
  оптимизируется при условии не ухудшить соответствующую компоненту incumbent;
  после таймаута сохраняется лучшее полное решение. `baseline_delay` задан
  точным `MaxEquality`, а не только нижними границами для вспомогательных
  переменных.
- С прежними исполнителями из исходного run 1: LNS выбрал 8 задач при бюджетах
  1 и 10 секунд, включая `DB-202`; оба плана не хуже Greedy по общей целевой
  функции. После сравнения в Docker опубликованы run 10 Greedy и run 11 LNS,
  у обоих 8 задач и 0 ошибок SQL-приёмки.
- Добавлена регрессионная проверка короткого бюджета; вместе с тестами модели,
  планировщика и сравнения — 63 passed.

## 2026-10-07 — регрессия 8 → 7 задач из-за ограничения стабильности

- По данным Docker: исходный LNS-прогон 1 содержит 8 задач; в сравнении со
  срезом 1 Greedy (run 2) содержит 8, LNS (run 3) — 7. Выпала `DB-202`.
- Причина в предыдущем исправлении стабильности: требовалось не меньше
  половины общего объёма задачи от каждого используемого прежнего исполнителя.
  У `DB-202` всего 247 часов, отдельные роли — 21, 30, 90 и 106 часов. Порог
  123,5 часа запрещал использовать прежних исполнителей этих ролей. Мягкий
  критерий ошибочно изменял множество допустимых решений; `OPTIMAL` относился
  к этой неверной модели.
- Теперь `kept(task, role)` эквивалентен условию
  `2 * sum(work предыдущей группы по роли) >= demand(task, role)`.
  При меньшей доле назначения остаются допустимыми, но пара задача/роль
  получает штраф за смену. Учитывается вся прежняя группа, а не только один
  человек. Независимый оценщик использует ту же формулу.
- Причина воспроизведена в памяти с исполнителями из run 1: старый код
  выбирает 7 задач. Текущие входы без этих предпочтений дают 8; поэтому простой
  повтор последнего запуска без восстановления исполнителей скрывал дефект.
- Добавлены три регрессионные проверки: маленькая роль в большой задаче,
  допустимая доля прежнего исполнителя ниже 50%, сохранение работы у группы
  из трёх человек. Вместе с тестами планировщика и сравнения — 62 passed.

- Ограничения часов и SP теперь округляются вниз до точности, сохраняемой

  границы Литтла к этой модели ещё не реализована.

### Оставшиеся ограничения перед эксплуатацией

- Модель пока дискретизирует работу до 0.0001 часа и не переносит эвристику
  `MIN_CHUNK_HH=1` существующего размещателя. На реальных данных нужно решить,
  является ли минимальный фрагмент бизнес-правилом, и либо смоделировать его,
  либо зафиксировать допустимое отличие.
- CP-SAT выбирает источник орбит глобально, а не воспроизводит по шагам
  процедурный порядок «сначала своя орбита» старого алгоритма. Минимизация
  займов стоит в целевой функции после критериев поставки. Сравнить это с
  ADR-001/015 и записать принятое продуктовое правило.
- Пропорциональные доли SP выбираются как floor/ceil по работе с точной суммой
  SP задачи. Это не повторяет побитно распределение остатка методом наибольших
  остатков в старом `_sp_shares`; валидатор проверяет ёмкость и сумму, но не
  идентичность конкретного правила округления.
- Если полный CP-SAT не находит допустимое начальное решение за свой лимит,
  построение завершается ошибкой; автоматического старого жадного seed/fallback
  пока нет.
- Новый режим пока не добавлен в сценарии чувствительности и workforce, а
  replay assistant snapshots по-прежнему принимает только старый алгоритм.
  До включения в UI/автоматические сценарии надо явно протянуть идентификатор и
  параметры поиска через эти входы.
- Для больших реальных наборов ещё не измерены время, объём модели и качество
  результата против greedy. Локальный repair улучшает найденный план, но сам
  по себе не доказывает глобальный оптимум.
