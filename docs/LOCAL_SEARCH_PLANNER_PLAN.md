# Альтернативный планировщик: локальный поиск с переоптимизацией расписания

Дата: 7 октября 2026. Ветка: `docs/local-search-planner-plan`.

Статус: план реализации; первая рабочая версия `lns-cpsat@1` находится в разработке. Ход фактических изменений фиксируется в `docs/CHANGELOG_ALGORITHMS.md`. Предложенные методы и предположения об ускорении требуют измерений на проектных данных.

## 1. Предложение

Добавить самостоятельный алгоритм `lns-cpsat@1`: он выбирает задачи и распределяет работу по людям и спринтам, затем улучшает результат, переоптимизируя части расписания. Для поиска внутри выбранной части использовать CP-SAT; для выбора частей — Large Neighborhood Search (LNS), с последовательным расширением окрестностей по принципу Variable Neighborhood Search (VNS).

Это не перестановка очереди с повторным запуском существующего жадного распределителя. Новый алгоритм сможет одновременно отменить несколько назначений, включить другие задачи, поменять исполнителей и распределение часов.

Существующий `greedy-priority-topo@2` оставить как контрольный алгоритм и явно обозначенный резервный вариант. Его план допустимо использовать как стартовую подсказку, но новый поиск должен уметь запускаться и без него.

### Роль нижней границы по методу Литтла

Уточнение пользователя: имеется в виду **нижняя граница по методу Литтла**. Использовать её как помощь поиску: оценивать перспективность подзадач, отсекать доказанно бесполезные ветви и показывать разрыв между найденным планом и оптимистичной оценкой.

Классический алгоритм Литтла решает задачу коммивояжёра методом ветвей и границ. Наш планировщик имеет делимую работу, параллельных исполнителей и несколько ресурсов. Поэтому ниже различаются исходная матричная редукция Литтла и предлагаемая адаптация принципа нижней границы к нашей модели. [Little, Murty, Sweeney, Karel, 1963](https://pubsonline.informs.org/doi/10.1287/opre.11.6.972).

Основной путь: LNS находит хорошие допустимые планы, а релаксация модели даёт границу для оценки и отсечения. Это гибрид локального поиска с ограниченным поиском по ветвям, а не утверждение, что задача проекта сводится к коммивояжёру.

## 3. Методы и выбор

| Метод | Применение здесь | Решение |
|---|---|---|
| Локальный спуск | Проверять соседние расписания, принимать улучшение | Финальная стадия и проверка малых окрестностей; сам по себе может застрять |
| VNS | Менять размер и тип перестраиваемой части | Использовать расширение от одной задачи к группе и цепочке |
| LNS | Зафиксировать часть расписания, остальные решения пересчитать | Основная схема поиска |
| CP-SAT | Совместно выбирать задачи, часы, исполнителей и спринты при дискретных ограничениях | Решатель подзадач LNS и полной модели на небольших примерах |
| ALNS | Адаптировать частоту операторов по их полезности | Второй этап после измерений; в первой версии достаточно фиксированного расписания операторов |
| Имитация отжига или tabu search | Выходить из локальных ловушек через ухудшения или память переходов | Возможное расширение, если простые перезапуски и увеличение окрестностей окажутся недостаточными |
| Полная MILP/CP-модель | Искать решение для всего горизонта с оценкой границы | Обязательный конкурент в эксперименте: для шести спринтов может оказаться проще и эффективнее LNS |

LNS строится на частичном разрушении и восстановлении решения; это позволяет менять сразу группу решений. VNS систематически меняет окрестности. Выбор гибрида для нашего проекта — инженерная гипотеза, которую нужно проверить на данных, а не известный заранее победитель. [Pisinger и Ropke, LNS](https://backend.orbit.dtu.dk/ws/files/5293785/Pisinger.pdf), [Hansen и Mladenović, VNS](https://www.sciencedirect.com/science/article/pii/S0377221700001004).

CP-SAT требует целочисленного представления и различает найденное допустимое решение, доказанный оптимум, доказанную невыполнимость и неопределённый результат поиска. Эти различия должны сохраняться в интерфейсе. [Официальная документация OR-Tools](https://developers.google.com/optimization/cp/cp_solver).

## 4. Целевая функция: сначала определить, какой план лучше

Не оптимизировать количество назначенных часов: занятость сама по себе не означает поставку результата. Не оптимизировать процент PI Predictability: маленький объём обещаний может дать высокий процент.

Предлагаемый профиль `business_completion_v1` — лексикографический максимум:

```text
F(plan) = (
    C[p_max], ..., C[p_min],
    -lost_baseline_initiatives,
    T[p_max], ..., T[p_min],
    -assignment_changes,
    -baseline_delay,
    -loan_hours,
    -completion_sprint_sum
)
```

- `C[p]` — количество целиком завершаемых инициатив уровня приоритета `p`.
- `lost_baseline_initiatives` — число первоначально обещанных инициатив, завершение которых теперь переносится за PI.
- `T[p]` — количество целиком размещённых задач уровня `p`; поощряет полезную частичную работу после сравнения законченных инициатив.
- `assignment_changes` — число смен основного исполнителя по продолжающимся парам «задача × роль» относительно предыдущего опубликованного плана; правило определения основного исполнителя фиксируется в спецификации.
- `baseline_delay` — сумма положительных сдвигов завершения ранее обещанных задач. Отсутствие даты в PI не трактовать как нулевой сдвиг: использовать согласованную штрафную дату за горизонтом.
- `loan_hours` — часы межкомандного займа.
- `completion_sprint_sum` — сумма спринтов завершения включённых задач; сравнивается после более важных критериев.

Приоритет инициативы вычислять по явному бизнес-значению или выбранной стратегии. `priority_strategy=task` неоднозначен для цели завершения инициатив: в MVP отклонять сочетание с новым профилем с понятной ошибкой, до отдельной спецификации агрегации.

**Это новая политика сравнения планов.** В ней завершение одной инициативы более высокого уровня важнее любого числа инициатив ниже. Защита старых обязательств стоит после бизнес-приоритетов, но перед частичной работой. До реализации зафиксировать эти последствия в ADR и проверить на примерах. Не представлять шкалу R1–R6 как рублёвую стоимость.

Разделить **поиск хорошего плана** и **доказательство его качества**.

Для доказательства лексикографического оптимума применять последовательные оптимизации: фиксировать старшую компоненту как доказанно оптимальную только после завершения соответствующего доказательства. Для рабочего поиска разрешить временно зафиксировать уже найденные значения старших компонент и улучшать младшие даже после таймаута старшего уровня. Такая фиксация — ограничение текущего поиска, а не доказательство оптимальности; следующие проходы снова могут улучшать старшие компоненты.

Другой вариант рабочего поиска — запрос существования строго лучшего вектора относительно incumbent:

```text
(F1 > b1)
OR (F1 = b1 AND F2 > b2)
OR ...
OR (F1 = b1 AND ... AND Fm > bm)
```

Здесь `b = F(incumbent)`, все компоненты уже приведены к максимизации. Любое допустимое решение запроса даёт улучшение без ожидания доказанного оптимума подзадачи. Доказанная невыполнимость означает отсутствие улучшения в заданной области; таймаут этого не доказывает. Кандидатов сравнивать общим точным оценщиком. Не использовать произвольные «огромные веса» с риском переполнения.

## 5. Модель допустимого расписания

Индексировать время спринтами, а не обычными неделимыми job-shop операциями: в проекте работа роли может делиться между людьми и спринтами, роли выполняются параллельно, внутри окна задачи допустимы разрывы.

Переменные:

- `z[t] ∈ {0,1}` — остаток задачи целиком размещён в текущем PI.
- `x[t,r,e,o,s] ≥ 0` — часы инженера `e`, списываемые с орбиты `o`, на роль `r` задачи `t` в спринте `s`.
- `w[t,r,e,o,s] ≥ 0` — эквивалент закрываемой работы; отдельно от затраченных часов.
- `a[t,s] ∈ {0,1}` — в спринте действительно выполняется положительная работа задачи.
- `q[t,s] ≥ 0` — доля SP задачи в спринте.
- `start[t]`, `end[t]` — первый и последний спринты положительной работы выбранной задачи.
- `y[i] ∈ {0,1}` — все необходимые живые задачи инициативы размещены; завершённые задачи учитываются по снимку факта.

### Жёсткие ограничения

1. Для выбранной задачи закрывается весь известный остаток каждой роли: `Σ w[t,r,e,o,s] = remaining[t,r] × z[t]`. Для невыбранной нет часов и SP.
2. Часы инженера ограничены одновременно общим фондом и бюджетом каждой орбиты в конкретном спринте. Использовать ставки `sprint_orbit_rates`, календарные множители и общий предел ставки. Межкомандный заём явно сохраняет орбиту-источник.
3. Назначения разрешены только при покрытии роли и всех подтверждённых требований к навыкам. Запрещённые замещения не включаются в кандидаты. Неразмеченные требования остаются явно неподтверждёнными.
4. Учесть нынешнюю семантику `efficiency`: часы исполнителя равны объёму работы, умноженному на коэффициент. Не заменять её привычной обратной формулой.
5. `Σ_t q[t,s] ≤ capacity[team,s]`; `Σ_s q[t,s] = remaining_sp[t] × z[t]`. Связь SP и работы должна соответствовать существующей формуле и правилам округления.
6. Для живой зависимости в режиме `finish_start`: выбор потомка требует выбора незавершённого предшественника; `start[child] ≥ end[parent] + gap`. Для завершённых предшественников брать фактическую нижнюю границу на дату среза. Режим `start_start`, если поддержан, моделировать отдельно и явно.
7. Работать только в открытых спринтах внутри PI. Завершённый факт и первоначальную базу обещаний не менять. Текущий исполнитель — предпочтение, а не обязательный запрет замены.
8. Неизвестный остаток работ не считать нулём: такую задачу не объявлять выполнимой.
9. В атомарном режиме связать выбор всех живых задач инициативы; в режиме частичного включения считать `y[i]` точным логическим AND выбранных задач.
10. Чисто процедурное правило «сначала своя орбита» отделить от жёстких бюджетов. При сохранении бюджетов и минимизации займа сравнить поведение с ADR-001/015; изменение политики права на заём зафиксировать до реализации.

### Числа, округления и границы модели

CP-SAT работает с целыми числами. Исходный кандидат масштаба — сотые часа и сотые SP, однако точность коэффициентов и промежуточных результатов нужно проверить по данным и `_sp_shares` до выбора масштаба. Запрещено незаметно округлять остаток вниз, чтобы он поместился.

Отдельная задача первого этапа — формализовать нынешнюю пропорциональную связь работы и SP, распределение остатка округления и минимальный рабочий фрагмент из `MIN_CHUNK_HH`. Определить, что является бизнес-правилом, а что ограничением текущего распределителя. Нельзя просто разрешить CP-SAT произвольные независимые доли SP: это даст преимущество за счёт другой модели.

Если точный перенос правил в целочисленную модель окажется слишком дорогим, описать консервативное приближение с отдельной версией модели и измерить потерю допустимых решений. Не называть такой эксперимент прямым сравнением алгоритмов при одинаковых условиях.

## 6. Как искать улучшения

### Начальный план

CP-SAT строит допустимое решение без требования повторять жадную очередь. В качестве необязательной подсказки передаётся старый план. При наличии валидного greedy-плана включить его в набор кандидатов на лучший результат, пересчитав тем же оценщиком.

Пустое расписание остатка может быть допустимой технической отправной точкой, но не должно публиковаться молча после сбоя поиска. Явно возвращать статус отсутствия нового пригодного результата или резервный план с указанием его происхождения.

### Окрестности

| Окрестность | Что разрешаем изменить | Для чего |
|---|---|---|
| N1: одна задача | Включение, исполнитель, спринты и доли работы одной задачи | Использовать свободные фрагменты ресурса |
| N2: две задачи | Все решения двух задач, в том числе обмен «включена ↔ перенесена» | Устранить неудачное раннее назначение |
| N3: одна инициатива | Все её живые задачи и необходимые взаимодействия с границей | Завершить бизнес-результат целиком |
| N4: дефицитная роль | Группа задач, конкурирующих за одних людей | Перераспределить узкий ресурс |
| N5: цепочка | Блокирующая задача и выбранные потомки | Сократить ожидание из-за зависимостей |
| N6: группа инициатив | Несколько конкурирующих инициатив | Проверить обмен одной дорогой поставки на несколько других |
| N7: обмен 1↔2 | Одна включённая и две перенесённые задачи, либо обратная комбинация | Преодолеть ловушку «80 часов против 40 + 40» одним строгим улучшением |

Внешние назначения фиксируются, их нагрузка вычитается из доступного фонда. Все зависимости между свободной и фиксированной частью остаются ограничениями модели. Если окрестность расширяется зависимыми задачами, сохранять фактический состав расширения в журнале.

Для начала использовать фиксированный цикл операторов, обязательно включающий N7, и воспроизводимую выборку по seed. При застое увеличивать размер освобождаемой группы. Затем перезапускать поиск из другого допустимого решения, сохраняя глобальный `best`. Внутри одного прохода принимать только строгие лексикографические улучшения; переходы через ухудшения — отдельный последующий эксперимент.

```text
deadline = now() + total_budget
prepared = prepare_inputs(snapshot, options)
best = best_valid_seed(cp_sat_initial(prepared, deadline), optional_greedy_seed)
if best does not exist:
    return explicit_no_valid_result()

for restart in restart_budget while search_time_remains(deadline):
    current = best if restart == 0 else feasible_restart(prepared, deadline)
    if current does not exist or not validate(current):
        continue
    best = better_valid_plan(best, current)
    for neighborhood in neighborhood_schedule(seed, remaining_search_budget):
        candidate, solver_status = repair_with_cp_sat(current, neighborhood, deadline)
        if candidate exists and validate(candidate) and F(candidate) > F(current):
            current = candidate
            best = immutable_copy(better_valid_plan(best, current))
        if not search_time_remains(deadline):
            break

best, certificate = final_local_descent(best, remaining_time(deadline))
return assemble_plan(best, diagnostics, certificate)
```

### Когда можно назвать результат локальным оптимумом

Условие: для явно определённой окрестности `N(S)` не существует допустимого `S'` с `F(S') > F(S)`.

Для небольших примеров эталонная проверка — финальный спуск по **всем** одно- и двухзадачным окрестностям, включая невыбранные задачи. Для каждой подзадачи доказать отсутствие улучшения. После любого улучшения начать проверку заново относительно нового плана.

Для рабочего режима сравнить этот перебор с одним запросом над полной моделью:

- Ввести `changed[t]`; при `changed[t]=0` зафиксировать весь блок решений задачи относительно проверяемого плана: выбор, назначения, орбиты, часы, спринты и SP. Производные значения пересчитываются согласованно.
- Ограничить `Σ changed[t] ≤ 2` и добавить условие `F(candidate) > F(checked_plan)` из раздела 4.
- Допустимое решение даёт улучшение; доказанная невыполнимость подтверждает локальную оптимальность по N1∪N2; таймаут оставляет результат непроверенным.

Это альтернативное представление той же окрестности, если блок задачи зафиксирован полностью и не добавлены новые ограничения. Его эквивалентность проверить независимым перебором. Для `k=3` аналогичный запрос охватывает и обмен 1↔2, но доказательство может стоить дороже. Скорость единого запроса относительно перебора заранее неизвестна; сохранить оба варианта в эксперименте.

- Если весь проход завершён с доказанными результатами, писать `local_optimum_verified`, указывать реально проверенную область (`N1∪N2` или все блоки до `k` задач), масштаб чисел, версию ограничений и objective.
- Если хотя бы одна подзадача завершилась по лимиту без доказательства, писать `best_found_budget_exhausted` или `no_improvement_found`, а не «локальный оптимум».
- Если проверялся только список случайных групп, это не сертификат локальной оптимальности.
- Оптимальность в `N1∪N2` не исключает улучшений группой из трёх задач или целой инициативой.
- Даже `OPTIMAL` одной repair-подзадачи не означает оптимальность полного расписания.

Сертификат хранит хеш итогового расписания и перечень проверенных окрестностей либо точное определение объединённого запроса с `k`, а также статус решателя; после изменения плана он недействителен. Статус поиска и статус проверки хранить отдельно: план может улучшиться, но остаться без сертификата.

## 6.1. Нижняя граница: адаптация идеи Литтла

### Что делает классическая редукция

Для квадратной матрицы стоимости назначения из каждой строки вычитают её минимум, затем из каждого столбца полученной матрицы — его минимум. Сумма вычтенных величин даёт нижнюю оценку стоимости назначения, следовательно и тура, который является частным случаем такого назначения. В ветвях учитываются принятые решения и накопленная редукция. Это опирается на требование выбрать ровно один элемент каждой строки и каждого столбца. [Оригинальная статья](https://web.tecnico.ulisboa.pt/~mcasquilho/compute/or/%2Ctsp/TSP1963OR_LittleEtAl.pdf).

В нашем случае строка «задача» и столбец «инженер» не образуют такую модель: одной задаче нужны несколько людей, один человек выполняет несколько задач. **Сумма минимумов такой произвольной матрицы не является доказанной границей качества квартального плана.** Нижняя граница длительности также не ограничивает автоматически потери бизнес-ценности: цель должна совпадать.

### Привести цель к минимизации потерь

Для одного уровня приоритета `p`:

```text
K[p] = количество инициатив уровня p в фиксированном рассматриваемом наборе
L[p](S) = K[p] - C[p](S)
```

Минимизация `L[p]` эквивалентна максимизации `C[p]`. В режиме доказательства при переходе к следующему критерию значения старших критериев фиксируются только после их доказанной оптимальности. В рабочем поиске разрешена временная фиксация найденного префикса; полученная граница тогда условна именно на этом префиксе. Для остальных максимизируемых компонент можно использовать смену знака или вычитание из фиксированного верхнего предела.

На одном скалярном уровне:

```text
LB ≤ L* ≤ UB
UB = потери лучшего допустимого плана
LB = доказанная нижняя граница потерь
absolute_gap = UB - LB
```

В терминах завершённых инициатив релаксация даёт **верхнюю** границу результата. Это то же неравенство после замены `L = K - C`. Слова «нижняя граница» в интерфейсе привязать именно к потерям.

### Первый вариант границы: расслабленная ресурсная модель

После измерения стоимости базового решателя рассмотреть отдельную LP-релаксацию исходной модели; не делать её обязательной зависимостью MVP:

- заменить бинарные переменные выбора задач и инициатив непрерывными в `[0,1]`;
- разрешить дробное распределение работы без минимального фрагмента;
- сохранить необходимые линейные условия покрытия ролей, фондов людей/орбит, ёмкости команд и связи выбора задач с инициативами;
- опустить зависимость по целочисленным датам и сложные условия округления, если их корректная линейная релаксация пока не реализована;
- для каждого отброшенного или ослабленного условия доказать, что ни один допустимый исходный план не исключается.

Если `Feasible(original) ⊆ Feasible(relaxation)` и стоимость совпадает на исходных планах, минимум релаксации не выше исходного минимума. **Для отсечения использовать доказанную двойственную границу LP, а не стоимость произвольного допустимого решения LP.** Численные допуски учитывать консервативно; сомнительная граница не отсекает ветку.

Первая реализация может использовать проверенную границу CP-SAT полной или ограниченной модели вместо отдельного LP-сервиса. Это граница конкретного решателя, а не матричная редукция Литтла. В отчёте различать `bound_method=lp_relaxation|cp_sat|little_assignment_reduction`. Поле `best_objective_bound` и направление оценки описаны в [контракте CP-SAT](https://github.com/google/or-tools/blob/stable/ortools/sat/cp_model.proto).

Ручная проверка: в примере с фондом 80 часов и инициативами 80, 40, 40 часов одного приоритета релаксация допускает максимум две инициативы. Значит, при `K=3` получаем `LB=1` потерянную инициативу. У greedy потери 2, у улучшенного плана 1. Совпадение `LB=UB=1` доказывает оптимальность **этого критерия на этом примере**; остальные критерии требуют отдельной проверки.

### Где буквально использовать редукцию Литтла

Предусмотреть дополнительный экспериментальный модуль `little_bound.py` для ограниченных подзадач, где удастся построить корректную релаксацию назначения:

1. Строки — фиксированный набор обязательных одинаковых единиц работы, столбцы — допустимые единицы ресурса. Указать единицу дискретизации и способ отображения любого исходного решения в назначение.
2. При избытке столбцов дополнить матрицу фиктивными строками с нулевой стоимостью. При необязательности работы добавить достаточное число фиктивных вариантов отказа с корректной стоимостью.
3. Стоимость клетки должна быть нижней оценкой **того же аддитивного критерия**, например затрат назначения. Запреты ставить только там, где назначение действительно невозможно.
4. Применить редукцию строк и столбцов; накопленную фиксированную стоимость учитывать ровно один раз.
5. Проверить границу полным перебором маленьких исходных задач.

Завершение инициатив — неаддитивный критерий: нельзя самовольно разнести штраф за незавершённую инициативу поровну по её часам. Поэтому буквальная матричная редукция не является обязательной частью первого рабочего решения для бизнес-цели. Она включается только после доказательства корректного отображения и стоимости, иначе остаётся сравнительным исследованием.

### Как граница помогает локальному поиску

Перед дорогостоящей переоптимизацией окрестности вычислять её границу с зафиксированной внешней частью, если ожидаемая экономия оправдывает стоимость этой проверки. По умолчанию обычная окрестность содержит текущий план; сравнивать полную стоимость с учётом фиксированной части, а не переменную часть с полной. Для текущего уровня цели при уже фиксированных старших уровнях:

```text
если current входит в neighborhood:
    LB > L(current): ошибка модели, масштаба, области или численной оценки
    LB = L(current): этот уровень не улучшить; проверить младшие критерии
    LB < L(current): улучшение возможно, но не гарантировано

если рассматривается ветвь, исключающая current:
    LB > L(current): ветвь хуже по этому уровню при том же старшем префиксе
    LB = L(current): нужны младшие критерии
    LB < L(current): ветвь остаётся кандидатом
```

Равенство позволяет отсечь только при поиске строгого улучшения именно этого скалярного уровня; в полном лексикографическом сравнении нужно проверить младшие уровни. Для общей оценки качества использовать границу **полной** модели. Граница окрестности не является глобальной границей.

Внутри небольшой repair-подзадачи можно явно ветвиться по включению задачи/инициативы, считать релаксацию на каждой ветви и использовать текущий допустимый план как incumbent. Если эту работу выполняет CP-SAT, второй ручной движок ветвей и границ в MVP не нужен. Отдельную реализацию делать только для сравнения с решателем.

Если ведём своё дерево: при прерывании нижняя граница получается из открытых ветвей с учётом закрытых решений, а не из последней просмотренной ветки. Необследованная ветка без границы не позволяет заявить конечный разрыв. Для нескольких независимых нижних оценок одной стоимости безопасно брать максимум; складывать их можно только при доказанном отсутствии двойного счёта.

Сохранять `bound_scope`, `objective_level`, `fixed_prefix`, `bound_method`, `lower_bound`, `incumbent_loss`, `absolute_gap`, статус и версию модели. Одного процента gap для всего лексикографического вектора нет; показывать границы по уровням и отмечать условность младших оценок.

## 7. Объяснения решений

Причины текущего greedy часто ссылаются на то, кто раньше занял ресурс. Для нового поиска такая формулировка может оказаться неверной.

Разделить объяснения:

1. **Доказанный структурный запрет:** нет роли, нет подтверждённого стека, неизвестен остаток, закрыт PI, невозможна нижняя граница по зависимостям.
2. **Выбор итогового плана:** задача не включена в лучший найденный вариант при заданной цели и бюджете поиска. Это не доказательство её принципиальной невыполнимости.
3. **Контрфактическая проверка:** принудительно включить задачу и пересчитать, показать потерянные инициативы и изменение целевого вектора. Статус `UNKNOWN` не переводить в «невозможно».

Для каждого улучшения сохранять: добавленные/снятые задачи, изменённые назначения, значения цели до/после, оператор и статус подзадачи. Контрфактический пересчёт лучше делать по запросу, а не по всем задачам при каждой итерации.

## 9. Проверки и эксперимент

### Набор задач

1. **Ловушка жадного выбора:** один спринт, фонд одной роли 80 часов, три независимые одно-задачные инициативы одного приоритета с потребностями 80, 40, 40 часов. Условия SP сделать заведомо достаточными. Порядок идентификаторов заставляет greedy выбрать 80; новая цель предпочитает две инициативы по 40. Зафиксировать прочие компоненты цели равными: обмен 80→40 не даёт строгого улучшения, поэтому N1/N2 может застрять. Проверить, что N7 или объединённая окрестность k=3 находит две инициативы; сертификат k=2 не должен выдаваться за решение этой ловушки.
2. **Цепочка:** короткий предшественник открывает ценную инициативу; поиск меняет распределение ресурса, не нарушая `finish_start`.
3. **Общий инженер:** две команды по 0,5 ставки не получают двойную суммарную ёмкость.
4. **Навыки:** часы есть, подходящего стека нет — улучшение через неподходящего исполнителя запрещено.
5. **Округления:** граничные доли SP и часов, несколько ролей, остаток менее минимального фрагмента; нулевая потребность и неизвестный остаток обрабатываются отдельно.
6. **Перепланирование:** факт закрытых спринтов неизменен; назначения только в открытом остатке; baseline не пересоздаётся.
7. **Структурный дефицит:** отсутствие роли не устраняется поиском; допустим результат без улучшения.
8. **Остановка:** таймаут, отмена и `UNKNOWN` возвращают лучший проверенный результат либо явный резервный статус.
9. **Сертификат:** на игрушечных данных полный перебор подтверждает N1/N2-оптимум; прерванная проверка не выдаёт сертификат.
10. **Атомарность и границы окрестности:** изменение предшественника не ломает фиксированного потомка; atomic не оставляет часть инициативы выбранной.

11. **Нижняя граница:** для маленьких задач проверить `LB ≤ optimum ≤ incumbent`; отдельно проверить знаки при максимизации, границу окрестности и всей модели, равенство старшего критерия при улучшении младшего, незавершённый LP и двойной счёт оценок.
12. **Редукция Литтла:** на допустимой модели назначения сравнить сумму редукций с точным минимумом; на неподдержанной многоресурсной модели модуль должен отказаться от выдачи сертификата.

13. **Объединённая окрестность:** множество улучшений при `Σ changed≤k` совпадает с полным перебором блоков до k задач; не пропущены часы, орбиты или SP.
14. **Временная фиксация цели:** младший критерий улучшается после таймаута старшего без ложного сертификата; следующий проход способен снова улучшить старший.
15. **Бюджет и повторное использование:** построение модели, warm start, greedy seed и проверки включены во время запроса; изменённый граничный ресурс исключает использование старого результата как сертификата.

Добавить интеграционные проверки новых результатов через `v_plan_violations` и существующие тесты публикации, SP, орбит, зависимостей, baseline и replay факта. Не ограничиваться тестированием модели её же собственным оценщиком: маленькие примеры проверять независимым перебором и ручными ожиданиями.

### Протокол сравнения

- Один хеш входа, одинаковый срез факта, режимы зависимостей, атомарность и цель.
- Исходный датасет, искусственная ловушка, примеры со сменой исполнителя и срезы после факта.
- Начальные экспериментальные бюджеты всего запроса: 5, 15, 60 секунд; это параметры исследования, не обещание скорости. Включать построение модели, стартовый план, расчёт границ, поиск и проверку результата. Отдельно измерять время каждого этапа и качество первого допустимого плана.
- Для стохастических вариантов — 10 фиксированных seed. Показывать медиану, худший результат, время и долю улучшений.
- Для воспроизводимых проверок: один worker, фиксированные версии и seed, детерминированный бюджет/лимит итераций. Один seed при остановке по настенным часам не гарантирует одинаковый результат.
- Полную модель запускать отдельно с большим бюджетом на небольших случаях. Разрыв до оптимума сообщать только при наличии корректной границы и с указанием доказанных уровней лексикографической цели.

Отчёт: полный вектор цели, завершённые инициативы по приоритетам, охват бэклога, потерянные обещания, изменения исполнителей, заём, нарушения, время, статус поиска и область сертификата. Рост числа задач без улучшения главной цели не считать победой.

### Критерии готовности

- Все жёсткие ограничения и SQL-инварианты соблюдены.
- На искусственной ловушке есть строгое улучшение по согласованной цели.
- При использовании валидного greedy как кандидата на `best` итог не хуже него по той же цели; деградация возможна только как явно зафиксированная ошибка, а не нормальное поведение.
- Есть запуск без greedy seed и результат не зависит от возможности запустить старый алгоритм.
- Нет ложных утверждений о локальной/глобальной оптимальности и невыполнимости.
- При сбое рабочий опубликованный план сохранён.
- Пользователь видит, что изменилось, почему и с какой уверенностью завершён поиск.

## 10. Риски и порядок приоритетов

Главный риск — улучшить цифры, изменив смысл ограничений. Поэтому сначала формализовать часы/SP и бизнес-цель, затем писать поиск.

Второй риск — недостаточно большая окрестность: полезный обмен может требовать перестройки всей цепочки. Проверять операторы цепочек и инициатив, а не только сдвиг одной задачи.

Третий риск — перепутать бюджет поиска с доказательством качества. Сертификат требует полного прохода по определённой окрестности; обычный таймаут означает только лучший найденный вариант.

Четвёртый риск — структурный дефицит исходных данных. Если требуемых ролей нет, новый алгоритм может дать тот же итог. Это корректный результат. Пользу метода следует демонстрировать также на контролируемых случаях, где перераспределение действительно помогает.

**Порядок реализации:** точная модель и разреженные переменные → полный CP-SAT → измерения → LNS с обменом 1↔2 и общим бюджетом → проверка локальной оптимальности → отдельная LP-граница и адаптивные операторы только при подтверждённой пользе. Нижнюю границу по принципу Литтла разрабатывать вместе с моделью: сначала корректность оценки, затем отсечения и измерение их пользы.

## 11. Улучшения по результатам разбора плана

Предложения в этом разделе — выводы из описанной модели. Эффект по времени и качеству ещё не измерен. Приоритет P0 — исправить до реализации поиска; P1 — включить в MVP; P2 — отдельный эксперимент после замеров.

| Приоритет | Изменение | Что устраняет или улучшает |
|---|---|---|
| P0 | Обмен 1↔2 и отдельная проверка k=3 | Ловушку 80→40+40, которую строгий поиск по двум задачам не преодолевает |
| P0 | Разделение улучшения и доказательства | Ожидание оптимальности старшей цели, пока младшие вообще не улучшаются |
| P0 | Проверка `LB≤cost(current)` для обычной окрестности | Ложные отсечения из-за несопоставимых или ошибочных границ |
| P0 | Проверка чувствительности бизнес-цели | Улучшение счётчиков вместо полезного результата |
| P1 | Разреженная модель и предварительные сокращения | Переменные заведомо невозможных назначений |
| P1 | Один общий бюджет и возврат лучшего допустимого плана | Неограниченное время на последовательные подзадачи и сертификат |
| P1 | Окрестности вокруг конкретного дефицита | Пересчёт слабо связанных задач без понятной причины |
| P1 | Подсказки из действующего плана и точные ключи повторного использования | Повторную работу без фиксации неудачных решений |
| P2 | Единый запрос проверки окрестности | До `n + n(n−1)/2` отдельных подзадач для проверки N1/N2 |
| P2 | LP-фильтр и буквальная редукция Литтла | Дорогие repair-запуски, только если цена границы окупается |

### 11.1. Проверить, что именно поощряет цель

**Дробление задач.** Компонента `T[p]` может вырасти, если одну работу разбить на несколько мелких задач при прежнем бизнес-результате. Добавить мысленный и тестовый пример такого разбиения. Если изменение предпочтения нежелательно, заменить эту компоненту ценностью подтверждённых промежуточных результатов с устойчивыми идентификаторами. До появления таких данных оставить счётчик задач лишь явно описанным вспомогательным критерием; не объявлять его бизнес-ценностью.

**Защита обещаний.** Вектор сначала максимизирует завершённые инициативы всех уровней, а потом сохраняет baseline. Поэтому добавление даже низкоприоритетной поставки может оправдать потерю прежнего обязательства при неухудшении старших компонент. Подготовить две политики для обсуждения: текущая `business_first` и `commitment_first`, где потери baseline стоят первыми. Не выбирать вторую молча. Версия objective должна хранить полный порядок компонент, а не только имя профиля.

**Стабильность людей.** Сохранение «основного исполнителя» не мешает заменить остальных людей или почти все их часы. Для оценки эксперимента дополнительно считать число добавленных/удалённых связей «задача × роль × инженер» и объём перераспределённой будущей работы. Сравнивать на общем открытом горизонте; завершённый факт и простое уменьшение остатка не считать сменой исполнителя. После замеров решить, стоит ли включать эти метрики в цель вместо грубого счётчика основных исполнителей.

### 11.2. Сократить модель до поиска

Создавать `x` и `w` только для сочетаний, где есть потребность в роли, допустимый инженер, положительный фонд орбиты и доступный спринт. Полный декартов набор «задача × роль × инженер × орбита × спринт» не нужен.

Если отсутствие роли или подтверждённого навыка доказано на всём оставшемся горизонте, сразу фиксировать `z[t]=0` с причиной. Распространять невозможность на живых зависимых потомков; в atomic-режиме — на всю инициативу. Не распространять такой запрет по неподтверждённым требованиям к стеку.

Сузить окна спринтов только доказанными нижними/верхними границами: открытый горизонт, фактические предшественники, зависимости. Оценка из прежнего расписания сама по себе не доказывает невозможность более раннего размещения.

Если коэффициент эффективности точно равен единице, `x` и `w` можно представить одной переменной с двумя смысловыми именами. Для других коэффициентов сохранять точное преобразование. Проверить числовые диапазоны до масштабирования и сокращать общие множители только без потери точности.

После каждого сокращения сохранять причину и проверять на малых примерах, что лучший допустимый результат не исчез. Не удалять похожих инженеров как «дубли»: различаться могут орбиты, будущая доступность, навыки и предпочтение прежнего исполнителя.

### 11.3. Выбирать задачи для перестройки по конфликту

Начинать с конкретной перенесённой задачи или незавершённой инициативы. Найти ограничивающие роль, спринт и кандидатов; добавить задачи, которые занимают тот же ресурс, затем необходимые части цепочки. Ограничивать размер группы измеримым числом переменных/назначений, а не только числом задач.

Граф взаимодействий должен учитывать общий пул допустимых инженеров, командный бюджет SP, зависимости и принадлежность инициативе. Одинаковой роли недостаточно для связи, а разные роли не гарантируют независимость: один человек может покрывать обе.

Для перезапуска менять условия поиска, seed и освобождённую группу. Передавать прежние назначения как подсказку, но не закреплять ими свободные переменные. Если перезапуск возвращает то же расписание, учитывать повтор по хешу и не расходовать на него весь бюджет.

Отдельные компоненты графа можно решать независимо лишь после доказательства отсутствия общих ограничений и разделимости цели. В MVP использовать граф для выбора окрестности; полную декомпозицию отложить.

### 11.4. Экономить бюджет осознанно

Одна общая конечная точка времени для всего запроса. После каждого этапа пересчитывать остаток. Начальное допустимое решение, LNS, границы и сертификат не должны получать по полному лимиту каждый.

Для эксперимента начать с долей 20% на подготовку/первое решение, 60% на улучшения и 20% на проверку; неиспользованное время передавать следующей стадии. Это настройки исследования, не норматив. При отсутствии валидного стартового плана можно отдать оставшееся время его поиску, явно оставив проверку оптимальности невыполненной.

Каскад проверок: структурная невозможность → дешёвая ресурсная оценка → доказанная граница решателя → отдельная LP-релаксация, если она оправдана. Порог перехода выбирать по статистике `время границ`, `число отсечений`, `сэкономленное время repair`. Если границы вычисляются долго и редко отсекают, отключить дополнительный фильтр без изменения математической цели.

### 11.5. Повторно использовать только сопоставимые результаты

Ключ подзадачи должен включать входной снимок, открытый горизонт, свободную группу, фиксированные внешние назначения, граничные зависимости, остаточные фонды, версию ограничений и фиксированный префикс цели. Если сохранён результат запроса «лучше incumbent», добавить в ключ и сравниваемый вектор.

Подготовленные допустимые кандидаты и структура неизменных ограничений подходят для повторного использования. Найденное расписание можно передавать как стартовую подсказку. Результат таймаута не считать доказательством; сертификат от старой границы окрестности не переносить на новую. Для MVP безопаснее повторное использование только при полном совпадении ключа, с ограничением памяти.

### 11.6. Минимальный полезный результат

Первый законченный эксперимент: точная CP-SAT модель, общий оценщик, разреженные переменные, один запуск без greedy, один запуск с подсказкой, граница решателя и сравнение на ловушке 80/40/40. Он проверяет, умеет ли новый подход принимать лучшее совместное решение.

Следующий: LNS с N7 и ограниченным бюджетом плюс оценка качества во времени. После этого — сравнение способов сертификата, LP-фильтра и адаптивного выбора операторов. Такой порядок позволяет отказаться от лишних механизмов, если полная модель уже даёт требуемый результат.
