# ПочтаТех · PI-Planner — слой данных

Квартальное планирование производства, прогноз рисков и «Звёздная карта»
компетенций. Этот репозиторий — **слой данных**: ETL из выданного Excel в
PostgreSQL и контракт, по которому бэкенд забирает результаты планировщика.

Исходники: `Демо_онбординг.pdf` (правила), `Хакатон_датасетс…xlsx` (данные).

## Быстрый старт

```bash
pip install openpyxl
python3 etl/load.py                # -> build/seed.sql

psql "$DSN" -v ON_ERROR_STOP=1 -f db/01_schema.sql
psql "$DSN" -v ON_ERROR_STOP=1 -f db/02_contract.sql
psql "$DSN" -v ON_ERROR_STOP=1 -f build/seed.sql
psql "$DSN" -v ON_ERROR_STOP=1 -f db/03_substitutions.sql
psql "$DSN" -v ON_ERROR_STOP=1 -f db/04_views.sql
psql "$DSN" -v ON_ERROR_STOP=1 -f db/05_invariants.sql
```

Можно залить одним шагом (нужен `psycopg2-binary`):

```bash
python3 etl/load.py --dsn "$DSN"
```

Локальный стек с PostgreSQL, приложением, Prometheus и Grafana:

```bash
cp .env.example .env              # задать пароли в .env
docker compose up -d --build prometheus grafana
```

Grafana откроется через Caddy на `https://grafana.localhost`. Prometheus не
публикует host-порт, а datasource создаётся автоматически. Настройка, проверки
и контракт метрик описаны в `docs/OBSERVABILITY.md`.

Перезалив идемпотентен: `seed.sql` начинается с `TRUNCATE … RESTART IDENTITY`,
гонять можно сколько угодно. Когда организаторы пришлют версию датасета —
просто положить новый файл и перезапустить ETL.

## Модель в двух словах

**Команда — ядро, инженер — спутник.** Ядро владеет ёмкостью в Story Points,
спутник владеет часами, грейдом и стеком. Привязка — `engineer_orbits` со
ставкой: 30 инженеров, 34 орбиты, четверо висят на двух ядрах по 0.5.

Два саттелита, не путать: **структурный** `engineer_orbits` (кто вокруг кого,
статично) и **временно́й** `task_state` (что с задачей было на каждый пересчёт,
insert-only).

## Календарь PI

`PI-2026-Q3` — **календарный** квартал: 01.07.2026–30.09.2026, 92 дня (ответ
организаторов №5, ADR-007). Спринты идут по 14 дней от начала, поэтому
92 = 6 × 14 + 8 и **последний, 7-й спринт короче — 23.09–30.09, 8 дней**.
Фонд часов пропорционален длине спринта: множитель 7-го спринта **0.5714**,
фонд ставки за квартал — **525.71 ЧЧ** (80 × 92/14), а не 560 «по числу
спринтов» (ADR-017). Множители считаются в БД — `v_sprint_fund_factor` и
`v_pi_fund_factor`; планировщик, витрины и инварианты читают их оттуда, а не
повторяют арифметику «92 / 14» каждый у себя.

## Что показывают данные

| | |
|---|---|
| Ёмкость в SP | перегруженных команд нет; самая загруженная — `Team-Platform`: 45 SP спроса против 47.31 SP ёмкости за квартал (95%) |
| Часы по ролям | **2371 ЧЧ** дефицита по **47** связкам «команда × роль» |
| Природа дефицита | **все 47** — «роли вообще нет в команде», не «мало часов» |
| Bus Factor = 1 | 8 ролей, спрос 1429 ЧЧ |
| Ролей нет в штате | 6, спрос 665 ЧЧ (в т.ч. `Руководитель проекта` — 449 ЧЧ) |
| Зависимости | живых рёбер 10 из 19, глубина ≤ 2 — **не** узкое место |
| **Нужен наём или дообучение** | **665 ЧЧ на 6 ролях**: РП 449 ЧЧ, поддержка 84 ЧЧ, 132 ЧЧ на четырёх 1С-ролях (`SRV-4043`, `SRV-4091`) |

Отсюда вывод для алгоритма: при жёсткой привязке задач к командам план
нерешаем в принципе. Узкое место — ресурсы, а не граф; вкладываться надо в
приоритизацию под ресурсным лимитом, а не в топологический solver.

Пять из восьми незаменимых инженеров вращаются вокруг `Team-Platform` — самой
загруженной команды (95% ёмкости за квартал). Это структурное бутылочное
горлышко всей организации.

**Три уровня нехватки лечатся по-разному** — не смешивать:

| Уровень | Механизм | Витрина |
|---|---|---|
| Человек есть, но в другой команде | заём между командами | `v_role_deficit` |
| Роли нет, но есть кому замещать | `role_substitutions` — **отклонено организаторами** | `v_role_deficit_effective` |
| Закрыть некем нигде | **наём** или дообучение — 665 ЧЧ, 6 ролей | `v_role_coverage_org` |

Замещения ролей организаторы запретили (ответ №2,
`docs/ANSWERS_ORGANIZERS.md`): в `role_substitutions` все 6 строк
`status='rejected'`, человека можно только дообучать — ADR-010. Механизм остался
в схеме как журнал решений и список кандидатов на дообучение:
`v_engineer_role_coverage` фильтрует `status <> 'rejected'`, поэтому план
строится только по родным ролям.

## Передача бэкенду

Отдать три вещи: `build/seed.sql` (или доступ к поднятой БД),
`docs/PLANNER_SPEC.md` (правила) и `docs/SCHEMA.md` (что читать и куда писать;
раздел 2б — готовый API для фронта). Фронт-команде — `docs/UI_SPEC.md`: шесть
экранов, нужные витрины, типы JSON и список того, что нельзя считать на клиенте.

Приёмка результата — одним запросом. Блокируют строки `severity = 'error'`;
строки `severity = 'warning'` план не отменяют, но показываются в UI:

```sql
SELECT * FROM v_plan_violations WHERE run_id = :run_id AND severity = 'error';
```

29 проверок (`A…AC`): ёмкость в SP, перегрузка инженеров по сумме орбит и бюджет
орбиты, допустимость роли, орбиты и займы, зазор зависимостей и перенесённая
блокирующая, нижняя граница старта, окна назначений и окно внутри квартала,
недоданные часы, пропущенные задачи, перенос без причины, базовая линия и её
неизменность, полнота KPI, слепок `task_state`, алерты. Три проверки —
`warning`: использованное замещение (сейчас таких быть не должно: все правила
`rejected`, ADR-010), выход за даты исходного плана и разрыв в окне задачи.
Полная таблица кодов — `docs/PLANNER_SPEC.md`, раздел 7.

Прогон планировщика — `uv run python tools/run_planner.py` (базовый план Недели 0,
он же фиксирует `plan_baseline`; `--dry-run` считает без записи). Результат
приёмки M2 — `docs/RUNBOOK.md`, раздел 9.

## Метрики, API для фронта и мониторинг

Сервер отдаёт пять эндпоинтов, и у каждого своя роль — путать их нельзя:

| Путь | База | Зачем |
|---|---|---|
| `/api/livez` | не трогает | liveness: 200, пока процесс жив |
| `/api/health` | читает | readiness: 503, если база недоступна |
| `/api/version` | не трогает | версии приложения, ETL и PI |
| `/api/views`, `/api/views/{view}` | читает | витрины для фронта: `?run_id=&limit=&offset=&order=` |
| `/metrics` | читает, с кэшем 15 с | Prometheus: process, HTTP, DB и бизнес-метрики `pi_planner_*` |

**Данные для фронта** отдаются одним маршрутом поверх белого списка из 25 витрин
(`app/views.py`, ADR-019): имя витрины — параметр пути, а не отдельный эндпоинт,
поэтому набор HTTP route labels не растёт вместе с экранами. Ответ — «строка витрины
как есть» плюс конверт (`as_of`, `run_id`, `count`, `columns`, `items`). Имя
витрины не подставляется в SQL, `ORDER BY` собирается только из колонок витрины,
чтение идёт в read-only сессии. Что показывать на шести экранах и чего фронт не
считает сам — `docs/UI_SPEC.md`; примеры запросов — `docs/SCHEMA.md`, раздел 2б.

Метрики собираются своим кодом (`app/metrics.py`, формат Prometheus 0.0.4, без
`prometheus_client`): HTTP-счётчики, живость базы, последний прогон планировщика
(`pi_planner_plan_violations{severity="error"}` обязан быть 0) и
`pi_planner_calendar_info{fund_factor="6.5714"}` — календарь виден на дашборде, а
не только в логах. `/metrics` отвечает 200 и при мёртвой базе: вместо бизнес-серий
приходят `pi_planner_db_up 0` и `pi_planner_db_metrics_error{error_class}`.
Все витрины дают одну HTTP-серию `route="/api/views/{view}"`. Отдельные
`pi_planner_view_*` используют имя только из закрытого whitelist, чтобы видеть
медленные витрины без пользовательской кардинальности.

Имена метрик заморожены для devops (ADR-018). Полный список с лейблами,
scrape-конфиг, алерты и Caddy-правило (`respond 404`, чтобы метрики не уехали в
публичный интернет) — `docs/OBSERVABILITY.md`. Логи: текст для демо или
`--log-format json` — одна строка, один объект.

SELECT * FROM v_role_coverage_org WHERE verdict LIKE 'НАЙМ%';   -- 665 ЧЧ, 6 ролей (замещения отклонены)
