## 3. Звёздная карта — самый сложный оставшийся экран

Тёмная палитра: корневой контейнер экрана обернуть в `className="starmap-scope"`
(уже есть в `tokens.css`, задаёт фон `--void`, текст `--star`, `color-scheme: dark`).
Все токены палитры объявлены на `:root`, поэтому они доступны и внутри SVG, и
внутри портала Drawer — но сам Drawer надо красить явно через `styles`, иначе
он приедет светлым (проверить на скриншоте).

**Раскладка детерминированная, НЕ силовая** (силовая «плавает» между
перерисовками, карту нельзя показать дважды одинаково — прямое требование
`docs/UI_DESIGN.md` §5.4):

- 6 ядер-команд по окружности фиксированного радиуса, угол ядра
  `-90° + i * 60°`, порядок команд — сортировкой по `team_id` (иначе
  раскладка поедет при перезагрузке);
- инженеры с `orbit_count === 1` (26 из 30) — равномерно по дуге вокруг своего
  ядра, дуга развёрнута наружу от центра, чтобы спутники не лезли в середину;
- инженеры с `orbit_count === 2` (ровно 4, у них `teams.length === 2`) — на
  связи между двумя ядрами: линия тянется к обоим ядрам, точка стоит на
  середине с небольшим перпендикулярным смещением, чтобы четверо не слиплись;
- радиус точки — грейд (`Senior` 15 / `Middle` 13 / `Junior` 2 инженера),

  смысла (`docs/UI_DESIGN.md` §9);
- SVG свой, без библиотек графов. Образец чистого SVG-компонента в проекте —
  `components/common/KpiStamp.tsx` (там же `polar()` и `ringOffset()`).

## 5. Не переделывай заново (решено и проверено)

- **Числа с сервера — строки, это ПРАВИЛЬНО** (`docs/UI_SPEC.md` §0.1:
  `numeric` из PostgreSQL сериализуется через `json.dumps(default=str)`).
  Читать через `num()` / `fmtHours()` / `fmtSp()` / `isNegative()`, никогда
  `+row.x`: `"140.00" + 1` даст `"140.001"`. Типы ответа — `src/types/views.ts`
  (сняты с живого сервера), НЕ `src/types/db.ts` (тот сгенерирован из схемы БД).
- **`useView`/`useViews`** — не возвращаться к ad-hoc `useQuery` с ручным
  `queryFn`. Именно это однажды уронило приложение: `UploadHistory` и
  `ActualsDropzone` держали один `queryKey: ['actual_uploads']` с разными
  `queryFn` (один резолвил в конверт, другой — в `.items`), а React Query
  кэширует по ключу, а не по функции. Падало как
  `Cannot read properties of undefined (reading 'length')`. Если похожее
  случится в новом коде — ищи дублирующийся `queryKey` с разными `queryFn`.
- **Гант через `display:contents`** — рабочий паттерн: каждая строка даёт
  ровно N+2 ячейки, автораскладка сама разносит их по столбцам. Не переписывать
  на `<table>` и на ручные `gridRow`.
- **Дизайн** — «Маршрутный лист», светлая тема везде, тёмная **только** на
  звёздной карте: решение пользователя, зафиксировано в `docs/UI_DESIGN.md`,
  альтернативы не предлагать.
- **Запреты `docs/UI_SPEC.md` §3** (это список запретов, а не пожеланий):
  не считать фонд квартала арифметикой, не зашивать число спринтов и нормы KPI,
  не пересчитывать `is_loan`/`is_substitution`/`is_native`, не суммировать
  `v_task_remaining_hh` по ролям, не выводить знаменатель KPI из
  `committed_week0`, не брать `plan_baseline` из прогона по умолчанию
  (канон — `MIN(run_id) WHERE as_of_sprint = 0 AND status = 'ok'`, в
  `usePlanData.ts` уже так), не вычислять «текущий прогон» самому, ничего не
  писать через `/api/*`, не кэшировать дольше вкладки.
- `docs/UI_SPEC.md` — документ, он местами отстал от кода (говорит про 25
  витрин и 2 прогона; на самом деле 33 витрины и 4 прогона). Источник истины —
  `GET /api/views` и живой сервер, затем `docs/DECISIONS.md` (ADR-020…025).
- `/api/health` показывает `"views": 22` — это число вьюх в PostgreSQL, а не
  размер белого списка. Витрин в контракте **33** (`GET /api/views → count`).
  Не «чинить» это расхождение.

## 7. Порядок работы

1. KPI — самый короткий, данные полностью разобраны в §4.1.
2. Роли и ёмкость, затем Профили — обе таблицы, данные в §4.2–4.3.

5. В конце: `npm run build`, обновить `web/dist` (он коммитится намеренно —
   демо-машина собирает фронт без доступа к npm, см. `.gitignore`),
   прогнать все семь экранов на 1440 px и на 390 px.
6. Удалить этот файл перед финальным коммитом.
